# AgentLink Tools Reference

This guide explains the built-in agent's tool families and points to the complete parameter reference. Tools are available only when the current mode, active skill, session type, and approval policy allow them.

## Read and understand a workspace

Use the lightweight orientation tools before broad changes:

- `read_file` with `view: "context"` — read an oriented file slice with metadata, diagnostics, symbols, and working-set status.
- `read_file` (default `view: "content"`) — read exact content, a bounded range, local images, or extracted PDF text.
- `list_files` — explore paths; `search_files` — search exact text or find code by intent.
- `get_repo_map` and `get_module_neighbors` — understand structure and dependency impact. JavaScript/TypeScript links resolve nearest `tsconfig.json`/`jsconfig.json` `paths` and `baseUrl`, including JSONC, exact/one-wildcard mappings, ordered fallbacks, and workspace-contained `extends` chains. Alias targets are checked against the canonical workspace boundary, including symlinks. Existing stored bare imports are resolved again when loading a map, so config-only changes refresh displayed links and reverse dependents. `get_repo_map` reserves budget for file skeletons and lists recognised dependency/cache/build-output trees (such as `node_modules`, `.npm-cache`, or SwiftPM `.build`) after project code; scope the map to one of those paths to inspect it directly.
  The standalone CLI and Assistant task runners offer the same two tools from a lightweight structural index that needs no embeddings or native database: built on first use, refreshed from changed files on every call, shared by every CLI and Desktop process on one checkout, task-scoped in the Assistant, and limited to the session's readable files. See [Standalone CLI](standalone-cli.md#code-map).
- Language tools — definitions, references, symbols, hovers, code actions, and rename support through VS Code.

**Indexed tools are workspace-only.** `get_repo_map`, `get_module_neighbors`, and query-mode `search_files` only cover files/folders within the current workspace folders. An absolute path to an external repository does not make its index available, even if it is open in another window or was previously indexed. `get_repo_map.include_external` includes dependency names, not external repository contents.

Use `search_files` with `query` for ranked code search when you do not know the location or exact wording, and with `regex` when you know the text or pattern. Exactly one of these inputs is required; both or neither is invalid. Query mode requires an explicit file or directory `path`, defaults `max_results` to 10, and accepts `exclude_globs`; regex mode defaults `max_results` to 300. Query limits are clamped to integers from 1 to 300. Query mode ignores regex-specific options with a warning, and `exclude_globs` is query-only (supplying it to regex mode produces a warning). External paths support regex search, `read_file`, and `list_files` subject to existing path permissions and approvals. `read_file` uses anchors or offsets to locate content in a known file, and `list_files` lists paths without a query mode.

Successful query results report the ranking actually used (`hybrid`, `lexical`, or `keyword_fallback`) and a bounded `ranking_reason` when applicable. Fallback results include repair guidance for the reported embedding or index category without exposing raw provider error bodies. Adjacent query terms and joined camel/Pascal-case identifiers boost indexed and keyword-fallback matches; snapshot and fixture paths are downweighted, not excluded. `embeddings_disabled` is intentional lexical operation, not a failure. Browser workspace chat mirrors native search; projectless Browser Ask Agent remains regex-only and has no workspace index.

In VS Code workspace sessions, mirrored browser workspace chat, and workspace-host sessions used by the CLI and Assistant, `read_file` is one tool with two views. `view` is optional and defaults to `"content"`; omitting it never switches to the context view. The former `get_context` tool is no longer advertised on those surfaces, and a direct call is rejected like any other unavailable tool. Older transcripts still show recorded `get_context` calls. The CLI and Assistant keep their existing project-relative path, scope, secret-redaction, and execution-backend boundaries; their default content reader remains narrower than VS Code's rich content reader, while `view: "context"` uses the VS Code-shaped context parameters, bounds, paging and output fields. Projectless Browser Ask Agent keeps its existing reader contract.

In VS Code, `anchor`, `anchor_regex`, and `anchor_offset` require `view: "content"` (or the default view), and `include_symbols` is available in both views. The standalone content view does not advertise anchors or symbol lookup. On every surface with the context view, select the starting line with numeric `offset`; standalone `include_symbols` applies to that view only.

Set `include_symbols: false` in the context view to skip symbol lookup and omit the outline. The default remains true. This does not change diagnostics, content pagination, or unchanged-content deduplication. The context view bounds its symbol outline independently of the content slice: at most 60 entries and 6,000 UTF-8 bytes of serialized symbol JSON. Symbols starting within the requested lines are prioritised, then remaining space provides a whole-file overview. `symbols_truncated` and `symbols_omitted` indicate entries omitted from the supplied outline; use `get_symbols` for a fuller language-service view where it is available.

Context-view content is capped at 2,000 UTF-16 characters per source line and 20,000 characters total (including line numbers). Very long or minified files therefore stay bounded even with a small line count. `content_truncation` reports omitted UTF-8 bytes, wholly omitted lines, and `next_read` arguments for the first omitted position. Pass those arguments back to `read_file` to continue within a long line. `character_offset` is a zero-based UTF-16 offset in the starting line, applied after secret redaction; explicit character pages bypass line-based unchanged-content omission. The default content view retains its exact-read behaviour.

Regex `search_files`, indexed query excerpts, and keyword fallback apply the same narrow structured-settings redaction as file reads, including context and multiline values; malformed or unreadable eligible configuration is withheld. Redaction covers credential-named keys (including environment-style names ending in `_KEY`, `_SECRET`, `_PASSWORD` or `_TOKEN`, except `PUBLIC_KEY`) and values with well-known provider key prefixes such as `sk-`, `ghp_` and `github_pat_`. This does not detect arbitrary secrets in source files. Because redacted values read back as `"[REDACTED]"`, `write_file` rejects a full rewrite of an eligible configuration file that would replace its existing secret values with that placeholder (`reason: "redaction_placeholder_overwrite"`); use `apply_diff` to edit the non-secret lines, or supply real values when the task is authorised to change them. Query excerpts are bounded to 4,000 source characters per result plus a truncation marker, with truncation counts. Recursive `list_files` honours an explicit root inside `node_modules` while still excluding nested dependency and Git metadata directories. Broken symlinks, permission-denied paths, and filesystem loops return bounded traversal warnings alongside discovered entries, including an empty pattern result. Such a listing is incomplete, not proof that the unreadable paths contain no matches. Invalid ripgrep arguments and process launch failures still return errors.

Exact parameters: [read and language tools](complete-reference.md#tools).

## Recover unsaved editor changes

VS Code workspace agents can use `get_editor_state` to inspect an already-open file-backed editor, including unsaved text that disk reads do not return. It supports disk files and buffers up to 8 MiB, with bounded line-numbered text and disk-to-buffer differences, the editor version, and separate whole-snapshot SHA-256 hashes for disk and buffer. `offset` and `limit` page buffer lines (maximum 200); each text preview is capped at 16,000 characters. Diff computation is bounded too: if it exceeds its work/time budget, `diff_omitted_reason: "computation_limit"` replaces the diff, while the inspected lines and hashes remain available. Eligible structured configuration secrets are redacted before either preview is produced.

Reviewed edits check the target document identity before changing its buffer and before an exact save. After a save failure, recovery guidance recommends `get_editor_state`/`save_editor` only when the same retained buffer is an open file-backed target within the recovery size limits. Otherwise it directs you to inspect and reconcile the preserved buffer in VS Code rather than repeat the patch against unchanged disk content. Restoring a previously active editor does not imply the retained document was discarded.

`save_editor` requires the inspected `path`, `editor_version`, `editor_hash`, and `disk_hash` (null only when the file is absent). It always asks for one-shot human approval, even with Approve for Me, and saves the existing buffer without formatting or ordinary save participants. The approval explicitly identifies that policy; check any required formatting separately afterwards. It does not replace or revert buffer content, persist trust, or apply a new patch. Refusal leaves unsaved work intact; changed disk/buffer state requires fresh inspection. A clean buffer already matching disk returns `already_saved`.

Files/buffers above 8 MiB, complete save approval text above 16,000 characters, and protected instruction/memory targets require the owning native workflow. A computation-limited save diff returns `editor_approval_diff_unavailable` without approval or saving; an oversized approval returns `editor_approval_too_large`. A truncated inspection diff is never sufficient to approve a save: the complete diff must fit the approval limit. Configuration whose inspection needs secret redaction or content withholding must be saved privately in VS Code, so raw secrets do not enter approval history. These tools require the VS Code editor host and are not provided by standalone CLI or helper-owned Ask Agent. Browser workspace supervision receives the existing approval events, but gains no editor mutation endpoint and its diff view stays read-only.

## Discover deferred native tools

Most AgentLink tools in the current request are exposed directly and must be called by name. `find_native_tools` searches only the compact deferred catalog named in its description; it is not a general availability check. When an exact query names tools that are already direct, or known native tools excluded from the current request, the result identifies those names and explains the next step. A tool can be present in one request and excluded from the next when the mode, active skill, background profile, or surface changes the authorized tool set.

Discovery and invocation guidance filter the captured catalog through the request's active allowance. A mode-blocked tool is reported as unavailable, not eligible, even when its definition remains in the cache-stable provider catalog. Calling an authorised direct tool through `call_native_tool` explains the direct route; excluded or dormant tools are not described as merely awaiting discovery. Command-validation recovery recommends file readers only when the current request authorises them. A restrictive skill may leave no callable read alternative: that restriction is reported rather than suggesting a prohibited reader or a policy bypass. None of this changes command rejection rules or widens permissions.

`get_module_neighbors` and the advanced fleet controls (`start_fleet_workflow`, `get_fleet_workflow_result`, `schedule_fleet_workflow`, `manage_fleet_automations`, and `detach_background_agent`) are deferred rather than included as full inline definitions. Discover the exact name with `find_native_tools`, then invoke it through `call_native_tool` using the returned schema. Existing mode, profile, skill, ownership, and approval restrictions still apply. Ordinary spawning and background supervision remain directly exposed when authorised.

If a model already knows a deferred tool's name and arguments, VS Code-backed sessions (including mirrored browser workspace chat) and projectless Browser Ask Agent also accept a direct call to that exact name. It uses the same captured deferred catalog, input validation, and execution path as `call_native_tool`; discovery is not a permission grant or a required prior step. Workspace sessions require the bridge to be available for this fallback. Unknown, excluded, dormant, mode-blocked, or skill-blocked tools remain unavailable, and ownership and approval checks still apply. The original provider call and result ID are preserved for conversation replay. Discovery followed by `call_native_tool` remains the normal route when the model needs the schema.

## Load session skills and rules

In VS Code workspace sessions and mirrored browser workspace chat, both `read_file` views can read reference files inside a skill directory from the current session catalogue without outside-workspace approval. This includes global and bundled skills and their canonical symlink targets. The exemption is read-only and does not grant access to unrelated outside-workspace files or permission to edit a skill. Mode, profile, and active-skill tool restrictions still apply.

`load_skill` remains available in restricted native profiles, including review and read-only research. `load_rule` is exposed only when the current request advertises deferred local rules, including in those restricted profiles; an empty rule catalog omits the tool entirely. These loaders read only artifacts authorised by the current session catalog, not arbitrary files. Enabled skills omitted from the bounded prompt projection remain loadable by their canonical paths. Skill content and real-path revision checks still apply.

When a skill path is rejected, `skill_not_in_catalog` returns up to ten catalog candidates matching the requested skill name or identity, plus an omitted count. This lookup reads no skill content and activates nothing. Retry with the intended candidate's exact path. If none match, refresh the catalog or check the skill's enabled state and mode. When the rejected path is a supporting file inside a catalogued skill's directory, the guidance says so and points to `read_file`. A valid advertised symlink alias returns the canonical activation path so its restrictions are applied consistently.

For an exact `SKILL.md` path excluded during the session's catalogue discovery, `skill_not_in_catalog` can also return `diagnostics` recorded for that file, with the code, severity, and validation message, such as `frontmatter field 'name' is required`. Only that exact discovered file path is matched lexically, without resolving symlinks. Relative paths use the session's workspace resolver; arbitrary paths, short-name guesses, supporting files, and unadvertised symlink aliases do not disclose these diagnostics. Directory-level discovery diagnostics are not returned by this file lookup. The response is bounded to eight diagnostics with up to 1,000 characters per message and does not reread the rejected file. Correct the problem through the normal reviewed workflow, then refresh the catalogue. This is discovery evidence only, not activation, a permission grant, or a way around mode/profile restrictions. Catalogue rebuilds replace the diagnostic snapshot; lightweight sessions with no skill catalogue have none.

`load_skill` activates only `SKILL.md` files. A successful activation returns `kind: "skill_activation"`, the skill's `skillDirectory`, and guidance for reading referenced files. Resolve a skill's relative references against `skillDirectory` and read them only when needed:

- **Built-in skills:** use `read_skill_resource` with the skill's `SKILL.md` path as `skill_path` and a path relative to its directory as `resource_path`, for example `references/tools.md`. It is available wherever `load_skill` is, including restricted profiles and active skill tool allowlists. It rejects absolute paths, `..` segments, symlinks that escape the skill directory, directories, binary files, unadvertised owners, and non-built-in skills. The owner's revision is checked first. Results are bounded text with `total_lines`, `showing`, `eof`, and `next_offset` for paging with `offset` and `limit`.
- **Global, project, and other skills:** use `read_file` with the absolute path under the skill directory.

Reading a resource never activates a skill, applies its tool restrictions, grants path trust, or counts as a loaded skill in the transcript. For compatibility, passing a built-in skill's reference path to `load_skill` still returns the file as `kind: "skill_resource"` with `activation: false` and a deprecation notice. This fallback is temporary; use `read_skill_resource` instead.

The standalone CLI, Assistant and Ask Agent use the same three tools, with the same descriptions, inputs and results. Each offers them only when it advertised a skill or deferred rule that turn. Two differences apply. These surfaces do not enforce a skill's `allowed-tools`, so the prompt asks the model to keep to them itself. Their sources also follow each surface's role: the CLI reads global and project sources, Assistant chats and tasks read only the project's, and Ask Agent reads global sources plus the built-in skills.

## Reduce related read-only fan-out

`compose` is a default-on foreground tool for known workflows with roughly four or more related reads. It runs a bounded JavaScript function body that calls authorized read-only tools, keeps child results out of provider history, and returns only the filtered, projected, joined, counted, or summarized JSON the model needs.

Compose is inline by default in workspace-backed foreground sessions whose mode and active skill permit it; no `find_native_tools` call is needed. Set the machine-scoped `agentlink.compose.enabled` setting to `false` to opt out, and reload affected VS Code windows after changing it. It remains unavailable to background agents, `/btw`, ACP, worktree setup, and projectless sessions. `AGENTLINK_DISABLE_COMPOSE=1` before startup force-disables it for recovery.

Use direct or ordinary parallel calls for one-offs, independent full results, and exploration where each result determines the next action. Compose cannot write, run commands, use web/memory/UI tools, nest itself, or open an approval. Text and extracted-PDF `read_file` calls are composable only without `query`; media/document output is rejected.

Compose can call `call_mcp_tool` for MCP tools that their server annotates read-only; `find_mcp_tools` marks these `read_only: true`. Other MCP targets fail the whole script before any child runs. Normal MCP approval still applies: a read-only tool that would need an approval prompt returns `interaction_denied`, so approve it once with a direct call (a session, project, or global approval then covers later compose calls). Results are text only, and children for servers without concurrency support run one at a time.

For independent reads, prefer `toolAllSettled`: it retains useful siblings when a file is missing or a child path needs interactive approval. A path-approval error returns `interaction_denied` with guidance to call that read tool directly; compose cannot obtain approval itself. Request, mode, skill, input and other policy violations remain fatal. Preserve per-child errors in the reduced summary. Reserve `toolAll` for batches where every result is required; it deliberately fails fast. Use paths established by prior reads/searches rather than guessed filenames. Child shapes differ: `search_files.results` is formatted text, not an array; `list_files.entries` is newline-separated text with paths relative to the requested directory, so split it, discard empty entries and prefix the directory before reading files. Syntax errors report bounded, script-relative line and column locations.

Compose cards in VS Code and browser workspace chat distinguish succeeded, failed, and cancelled children. Child errors wrap below the affected read instead of disrupting row alignment. The script is readable JavaScript under **Script**; failed results show the error first, with raw JSON and stack traces under **Technical details**.

The final output limit is 40 KiB. If exact secure retention succeeds, oversized output returns completed-with-spill metadata (`outputSpilled: true`) and a bounded preview plus `recovery.output_file`, rather than an execution failure. Read only needed artifact records instead of rerunning completed work. Retention failures and genuine execution errors remain errors; cancellation remains cancellation. Byte limits are unchanged.

Exact script helpers, child constraints, limits, and recovery behavior: [compose](complete-reference.md#compose).

## Make reviewed changes

- `write_file` creates or replaces a file through the reviewed editor save boundary.
- `apply_diff` applies reviewed search/replace blocks or unified diff hunks. Tool-description renderers may prefix examples with `//`; those prefixes are documentation comments, not part of the diff string. Send marker lines without `//`, while preserving comments that belong to the actual search/replacement payload. The first SEARCH opener or unified hunk header selects the format: `@@` hunk headers inside SEARCH/REPLACE blocks are literal payload, so patch files can be edited without switching to `write_file`. Properly prefixed reserved markers inside unified hunks remain payload too.
- `find_and_replace` makes a bounded multi-file replacement proposal. In regex mode, `$1` through `$99` refer to captures and `$$` emits a literal dollar. Nonexistent capture references and `$0` stay literal; existing unmatched optional captures become empty. Two-digit references fall back to the first capture digit when needed. Other dollar tokens stay literal. Like VS Code's regex replace, `\n`, `\t` and `\\` in the replacement become a newline, tab and backslash; other backslash sequences stay literal. With regex off, replacement text is always literal. Set `save_without_formatting: true` to save every changed file without format-on-save and verify it exactly; the result then reports per-file `durability`, and any failed or altered save returns `partial`/`error` with `saved_files` and `failed_files` instead of claiming success.
- `rename_symbol` uses VS Code language intelligence where available.

`propose_memory` is the explicitly approved workflow for authoritative instructions, skills, and commands. For a project skill, set `skill_directory: ".agents/skills"` to propose a team-shareable `SKILL.md` instead of the default `.agentlink/skills`. The selector is valid only for `tier: "skill"`, `scope: "project"`; global proposals and projectless Browser Ask Agent cannot use it. Add/update/remove targets the selected directory exactly, without searching another same-named skill. Update/remove of a missing target fails rather than creating or silently removing anything. Normal review and verified-save boundaries still apply; see [authoritative configuration](customization.md#reviewed-authoritative-configuration).

In VS Code, automatic write/edit review opens, saves, and tab cleanup preserve keyboard focus so they do not interrupt typing in chat. Save without Formatting (including exact-preservation saves for Unity files) makes the target editor active without requesting keyboard focus, and preserves focus when restoring the previous editor. If the target does not become active, the save fails safely rather than saving another file. Explicitly opening a pending diff still focuses it. Browser diff review remains read-only.

For transformed ordinary saves, results report `format_on_save_changed_lines` and `reviewed_changed_lines` (`added` and `removed`). The reviewed count can be omitted when the bounded diff times out. If formatting changes exceed 10 times the reviewed changed-line count (using a minimum denominator of 1), the result warns and requires a reread. A separate count warning is included whenever the formatting patch is omitted by the 4,000-character preview cap. These reports do not roll back saved content or change ordinary save behavior.

Accepted writes include durability evidence. If format-on-save changes approved content, re-read when the result requests it. When saved formatting conflicts with the repository formatter or a save participant restores the baseline, inspect the saved file and save-participant configuration, then compose a new reviewed edit with `save_without_formatting: true` if exact preservation is intended. Do not repeat the same ordinary save or automatically change the user's formatter configuration. Protected targets, outside-workspace paths, and other policy boundaries remain reviewable. Foreground Review mode exposes `write_file` only for absolute paths inside the host temporary directory, such as Markdown bodies passed to review or approval commands; workspace files remain read-only. Normal write approval still applies. Background agents using the `review` tool profile remain fully read-only.

The standalone CLI exposes a narrower terminal-native contract: project-relative `read_file` content/context views, bounded regex search, and single-file `write_file`/canonical SEARCH-DIVIDER-REPLACE `apply_diff`. `read_file`'s context view carries the saved baseline hash in `working_set.content_hash`; the separate `get_context` name is gone. Existing files require that saved baseline hash, new files require an absent-file precondition, and the terminal shows the complete resulting diff before approval. A session grant continues only the same tool and path along its verified content-hash chain; external edits, changed scope or policy, and switching between patch and replacement require a fresh review. CLI writes preserve exact content and return a verified final hash; they do not run VS Code format-on-save. After explicit managed TypeScript/JavaScript installation and separate typed enablement for the canonical project, the CLI also exposes read-only `get_diagnostics`, `get_symbols`, `go_to_definition`, `get_references`, and `get_hover`. These use project-relative paths, return explicit freshness/readiness metadata, and recheck file scopes before returning locations.

VS Code write/edit results report diagnostic samples only for the edited file, with bounded samples and pre-existing-error/line-shift filtering. They do not label errors from other files as caused by that edit. Diagnostic updates are observed over a bounded window, but the VS Code API supplies no source version for each diagnostic: an event or quiet interval is not compiler proof that an error belongs to the saved text or was caused by the edit. Non-empty samples are qualified accordingly, especially when no post-change event arrives, collection times out during updates, or the editor changes. A clean edit with no diagnostic event does not produce a pending warning. Disk durability is verified independently of diagnostic readiness.

Newly opened files get a bounded wait for pre-edit diagnostics before applying the proposal. An open document alone is not a clean diagnostics baseline. If no baseline becomes available, errors outside the edited lines are omitted and reported samples are explicitly unconfirmed as introduced by the edit. If the buffer changes during that wait, the proposal is not applied and the buffer is preserved. `read_file` diagnostic counts are cached language-service observations with unverified source freshness; matching open-editor dirty state flags that unsaved text may differ from the returned disk content. Neither reading correct disk text nor observing an editor version validates diagnostic source freshness. Use workspace diagnostics tools or the project's compiler/tests separately when checking wider effects.

Exact write-tool parameters and marker grammar: [write tools](complete-reference.md#write_file). Standalone CLI details: [Standalone CLI](standalone-cli.md).

When a VS Code edit save fails, `save_failure.save_outcome` distinguishes `returned_false` from `exception`. A supplied exception message is capped at 500 characters, with recognised credentials redacted, and returned as `vscode_error_message` with `vscode_error_detail: "available"`; missing messages remain `"unavailable"`. This is narrow redaction, not a guarantee that arbitrary formatter output is secret-free. The dirty buffer remains available for inspection and reviewed recovery.

## Generate, present, and save images

- `generate_image` is available in Code and Architect modes and defaults to GPT-Image-2.5 Flare for fast visual exploration. Use Sunburst when editing precision or final polish matters. OpenAI API-key sessions can select validated dimensions, quality through `max`, input fidelity, background transparency, PNG/JPEG/WebP output and compression, or explicitly edit a selected image with an optional PNG mask. ChatGPT/Codex OAuth keeps legacy generation and reference-led refinement; advanced controls are rejected before spending quota until that backend is verified.
- **Images in replies.** Agents show images with Markdown: `![description](source)`. The source can be a web image URL, a chat image ID such as `image_3` (attachments, screenshots, generated images, MCP image results), or a local PNG, JPEG, GIF or WebP file inside the workspace or the temporary folder. Every chat surface shows it with the standard image viewer (enlarge, open in editor, copy, print, download) and a source link under web images. The chat view never loads image URLs itself; AgentLink retrieves them on this computer with the public-only rules below. A web image loads automatically when its URL already appeared in the chat (for example in search results or an `inspect_page_images` result); any other URL shows a **Load image from …** button. Browser Ask Agent and Desktop support web URLs and chat image IDs, not local files.
- `present_images` is for when the agent also needs to look at an image. It takes chat image IDs (`image_ids`, `use_recent_images`), web image `urls`, `inspect_page_images` `candidate_ids`, or local `paths` (VS Code only), sends the images to the model, and shows them in the chat with any source caption (page link, title, and publisher-supplied creator or licence). It does not generate images or use image quota.
- `inspect_page_images` helps an agent find real images on the web, such as clothing, album covers, or existing artwork. Typical flow: `web_search` (or an MCP search) for candidate pages, `inspect_page_images` to list a page's primary images from structured data, Open Graph, Twitter cards, and large `<img>` elements, then put the best `image_url` in the reply as Markdown. The image is captioned with the page it came from. Retrieval runs on this computer without scripts, cookies, or credentials; only public addresses are allowed, redirects are re-checked, and PNG, JPEG, and still WebP images up to 4 MB are accepted. Pages larger than 4 MB are read up to 4 MB, which covers the metadata at the top of the page. Controlled by `agentlink.webAccess.imageRetrieval`: `enabled` (default) works without asking, like `web_search` and `web_fetch`; `prompt` asks before `inspect_page_images` or `present_images` contacts a new site (**Allow once** or **Allow public images for this chat**) and shows a load button for every web image in replies; `disabled` turns web images off. `inspect_page_images` is hidden when that setting or `agentlink.webAccess.fetchBackend` is `disabled`, and `agentlink.webAccess.allowedDomains`/`blockedDomains` apply to every page, image and redirect. Browser Ask Agent and Desktop retrieve from the browser gateway helper and show any approvals there. SDK hosts get the same tools and a Markdown image renderer helper from `createNodeHostWebImageTools(...)` in `@agentlink/node-host` ([embedding guide](embedding-agentlink.md#find-and-show-web-images)). Not yet available in the standalone CLI.
- `save_session_image` (VS Code, Code and Architect modes) writes an image already in the session, such as a pasted attachment, a screenshot, or a generated image, to a workspace file by its `image_N` ID. Bytes are written as stored, the file extension must match the image type, and existing files are replaced only with `overwrite: true`. It follows the same write approvals as file edits.
- Session image IDs stay the same after context condensing; the condense summary lists older images by ID without putting the images back into context. Details: [session image IDs](complete-reference.md#session-image-ids).

VS Code can save generated PNG, JPEG, and WebP files and use workspace-local edit/reference images. Browser Ask Agent remains display-only and uses retained session image IDs. Advanced calls require approval each time; legacy generation can still use **Generate for Session**. Partial streaming frames are never reported or saved as completed assets. Exact parameters: [image tools](complete-reference.md#generate_image).

## Run and inspect commands

Unmatched public network destinations under Approve for Me receive Guardian review before the exact numeric dial. The optional Jev first pass can allow clearly bounded, task-authorized destinations; full Guardian handles other reviews. High/critical risk, uncertainty, denials or unavailable review reach the ordinary network approval card. Prompt rules still ask, Forbidden rules reject, and private/LAN/metadata destinations remain blocked. Each socket and redirect to an unmatched destination needs its own decision. A low- or medium-risk Jev or Guardian allow saves an exact session-scoped destination rule (protocol, host and port), so later sockets to that site in the same chat skip review; the rule appears with other session rules, can be removed, and never becomes a project or global rule. Encrypted HTTPS/TCP paths and payloads are not visible to the reviewer.

For web research and reading pages, prefer `web_search` and `web_fetch` when they are available. They do not run through the sandbox, so they need no per-site network approval. Keep `curl`, `wget` or scripts for APIs, downloads and package tooling that genuinely need a shell.

With **Approve for Me** in foreground built-in **Review** mode, a verified request such as `review https://github.com/owner/repository/pull/42` can authorise supported `gh pr comment`, `gh pr review`, and equivalent REST `gh api` publication calls on that PR without asking again solely to publish. Guardian still reviews the exact action and risk. The host uses bounded, completed task observations to confirm the PR and scope, not an assistant rationale or a loaded skill. For comment edits, use an explicit-ID API PATCH with same-task ownership/current-content evidence; `--edit-last` can select a human-written comment and keeps normal handling. Pending-review submission must not publish a human-created or changed draft. This slice covers only agent-created drafts without inline comments or file-backed creation payloads, with a fresh exact review read and a completed `--paginate --slurp` comments read proving every page empty. Drafts with inline comments retain ordinary handling; a new review with inline comments can still qualify. File-backed bodies are bounded and revalidated. Inherited `GH_HOST` participates in target matching. Named or explicitly targeted terminals and temporary HOME requests keep ordinary handling because this slice cannot bind their shell/account state. Missing or ambiguous evidence falls back to ordinary review, with no hidden GitHub lookups. Explicit rules, manual mode, network/recovery approvals, and read-only profiles retain precedence. See [approval capabilities](capabilities.md#approvals).

Native commands check that the shell's current directory and the requested working directory refer to the same filesystem object, rather than trusting matching path strings. If a directory was deleted and recreated, the shell re-enters it using the logical path. If recovery fails, the command returns a nonzero exit without running the payload. When the directory still matches, no redundant `cd` changes `OLDPWD`, zsh directory hooks, or the directory stack. Unnamed commands still isolate shell mutations; named/targeted terminals still retain intentional shell state.

With Approve for Me active, normal index-only `git restore --staged` / `-S` is routine Git workflow and needs no Guardian model call, including on the native escalation required for Git metadata writes. Working-tree flags (`--worktree`, `-W`, or combined `-SW`), source overrides, and unsupported options remain reviewed. Guardian can approve restoring named workspace files only when task history and inspected changes establish that every discarded edit is disposable work from the current task. Broad restores, unrelated or mixed edits, and uncertain ownership still need direct user authorisation. A reason saying "cleanup" is not proof. Explicit rules, protected-file checks, and manual approval behaviour are unchanged.

When only some parts of a compound command match an Allow command rule, automatic approval judges the remaining parts. For example, with an Allow rule for `terraform plan`, `terraform plan && git commit -m "x"` is approved as routine Git workflow without a Guardian call, and the result's `approval` reports `rule_allowed_subcommands`. A rule covers a part only when it matches that complete shell segment, so a rule for `npm test` does not cover `sudo npm test`. When a pipe joins the parts, or an uncovered part changes directory (`cd`, `pushd`, `popd`), the shortcut does not apply: Guardian reviews the whole command, sees which parts are rule-allowed, and judges how the parts combine rather than the allowed parts' own risk. Prompt and Forbidden rules, sandbox recovery approvals, and earlier one-time approvals (which still match only the exact full command) are unchanged.

Named or explicitly targeted **Native Agent** terminals retain intentional shell changes. Sandbox commands always use fresh shells, including when a terminal is named or targeted: an `export PATH=...` in one sandbox call does not change the next call. Supply non-reserved variables through `env` on every call (literal values, not shell expansion), or put dependent steps together in one reviewed command. Sandbox `PATH` is host-managed and reserved: do not pass `env.PATH`. To change executable lookup, include `export PATH="/desired/bin:$PATH" && command` in each reviewed sandbox call. Other host-managed entries, including HOME, temporary directories, proxy settings, and loader settings, remain reserved. Terminal identity and retained output are separate from shell-state persistence.

Prelaunch `sandbox_preparation_failed` results include a bounded `preparation_failure`: `reserved_path_override`, `reserved_environment_override`, `unsupported_shell_profile`, or `preparation_failed`. Known input/configuration errors are not attestation failures. Unknown preparation exceptions remain blocked with bounded host/request inspection guidance; raw exception text and environment values are not returned or logged by this classification. Existing typed security, integrity, drift, and grant errors keep their own recovery paths. None of these preparation failures authorises native fallback or automatic replay.

Prelaunch `sandbox_unavailable` results include a bounded `sandbox_diagnostic.category` when available, not raw probe output or exception text. Their non-automatic repair guidance distinguishes missing host Node runtime from failed security checks. `compile_failed` grant failures require checking request/policy mismatches before runtime assets, not repeated commands, assumed reinstallation or native bypass. Only the bounded reason is logged, not the raw compiler exception. Native shell startup timeouts require inspecting and repairing the selected shell profile's startup; reloading alone cannot fix a startup prompt or hang. See [terminal recovery](troubleshooting.md#a-terminal-tool-call-hangs-or-times-out).

- `execute_command` runs a command in a managed terminal. Under Approve for Me, default commands with complete direct Allow or Prompt rule coverage run natively; unmatched or partially covered commands stay sandboxed. Explicit sandbox-only requests and read-only execution stay sandboxed. An Allow rule skips the command card, a Prompt rule still asks, and Forbidden rules block execution. Command approval checks are ordered within each chat session, not across tabs: a pending approval in another tab does not block this session's checks or approval card. All authorization and shared workspace scheduling constraints remain in force. For an eligible default Approve for Me command, a confirmed sandbox runtime failure before command start offers one direct native approval, not a retry loop. The user must approve the exact command; rejection cannot be prompted again for that action in the same turn. Trust, security, invalid grants, uncertain launch state, and commands needing sandbox-only capabilities do not receive this fallback.
- `get_terminal_output` reads retained output or controls an observed command. Pass the `command_id` returned by native/sandbox `execute_command` together with `terminal_id` to read the same command after terminal reuse. Omitting it selects the latest command. An unavailable or expired command ID returns an error rather than another command's output; `kill: true` cannot interrupt a newer command when an older ID is selected.
- `close_terminals` closes managed terminals when appropriate.

The standalone CLI has a separate non-PTY command contract. Its `execute_command` uses an exact reviewed `/bin/zsh -c` launch with closed stdin, no persistent shell state, a project-contained working directory, and no sandbox claim. Environment values are omitted from approval and prepared-launch persistence; approvals retain variable names plus a host-keyed digest and revalidate the resolved environment before launch. Values of credential-like environment variables are redacted if a command prints them. `get_command_output`, `list_commands`, and `stop_command` operate on stable session-owned command IDs. Foreground commands hold the project mutation window until exit. Background development processes require typing `allow background` for each exact launch and remain observable through `/processes`, `/output ID`, and `/stop ID`. Retained interleaved output is bounded and reports dropped offsets; restart marks prior running records interrupted without reconnecting or replaying them.

Command history and output retention are bounded, not permanent storage. Earlier command IDs remain readable while their records are retained in an open terminal; closing or reclaiming a terminal retains only its latest command. Read final output before closing and use a returned `output_file` when available. Cleaned command text retains leading whitespace, blank lines and final newlines, with PTY CRLF line endings normalised to LF; saved output is cleaned text, not byte-for-byte raw stdout.

AgentLink redacts recognised Kubernetes Secret `data`/`stringData` in YAML or JSON terminal results and spills, and removes the object dump from recognised failed Secret Go-template output. It also redacts nonempty values on environment-style `NAME=value` lines whose names are `TOKEN`, `SECRET`, `API_KEY`, `PASSWORD`, or end in those underscore-delimited suffixes (case-insensitive, with an optional `export` prefix, starting at column one). Empty values remain visible for auth debugging. This happens before output filtering, in saved output files, in later `get_terminal_output` reads and when a command is force-completed. Force-completed partial output is bounded and does not claim a final output file. This is narrow accidental-disclosure protection, not a guarantee that arbitrary command output is secret-safe: unlabelled values, diff-prefixed or indented assignments, arbitrary formats and multiline environment values are not generically redacted, and the local terminal's raw output remains visible. Native/sandbox signal deaths include `signal` and a nonzero `exit_code` (128 + signal when the PTY supplied zero or no exit code), so an aborted process cannot look successful. Carriage returns move the output cursor without erasing text that has not been overwritten.

Command route, network access, shell persistence, and approval behavior depend on policy. Native Agent commands are dispatched through verified private command artifacts so complex approved shell text is not retyped through the interactive line editor. Readiness requires a nonce-bound confirmation emitted from the consumed artifact, not merely the outer shell-wrapper start. If dispatch ends without that confirmation, execution state stays unknown (`process_launched` is omitted), the result identifies a launch-stage failure with `retry_safe: false`, and captured launch diagnostics remain available through the normal output store. Inspect those diagnostics and any side effects before a new execution; no automatic replay is safe. Disposing a running process does not remove its input artifact before shell completion or terminal closure; unstarted proposals still clean up immediately. Bare SSH sessions remain blocked, while a command supplied after the SSH host is treated as one-shot/non-interactive. Safe `git init` chains targeting the workspace root receive protected-metadata native-retry guidance before launch. Use the structured recovery guidance returned by a failed command instead of guessing at retries. Recognized recovery includes bounded Turbopack listener cause chains, tsx Unix-socket denials, mise-wrapped container access and trusted-config writes, npm cache writes on managed-network routes, and Speakeasy/macOS TLS trust failures. Guidance never grants Unix IPC or container sockets, disables TLS checks, or automatically replays a compound command; isolate the failed step when earlier steps may already have succeeded.

Protected Git metadata preflight also recognises narrow Git-only `&&` and `;` workflows mixing writes (`add`, `commit`, local `user.name`/`user.email` setters) with inspections (`status`, supported `diff`/`ls-files`/`log`/`show`, author/committer `var`, and `remote -v`). It also recognises literal `printf` input piped to `git add --patch`/`-p` with file operands, including `git -c color.ui=false`. The same inspection allowlist supports quoted `test -z "$(git ls-files …)"` and `test -z "$(git diff …)"` guards before a writer. A constrained `git ls-files -z [-- paths] | xargs -0 git add --` pipeline is recognised too. Arbitrary or nested substitutions, script-running `xargs`, other configuration overrides, other dynamic input/output pipelines, and repository redirection remain outside that narrow preflight. A match only offers reviewed native execution before launch, never automatic permission or replay. Post-launch index and `ORIG_HEAD` lock denials, including linked-worktree metadata, receive Git recovery before generic HOME suggestions. When Git prints an internal `git apply` failure despite a zero shell exit code, the original exit code is preserved alongside `failure_evidence` and non-automatic recovery guidance. The same applies when a later command masks a recognised Git permission-denial diagnostic tied to protected metadata: `failure_evidence.code` is `protected_git_write_denied`, and recovery remains `protected_git_metadata`. Detection uses retained output before display filtering and does not claim which other steps succeeded. Inspect repository state before any reviewed retry because earlier hunks or workflow steps may already have changed it. GitHub TLS recovery recognises a `gh` step in a mixed workflow or review loop when the failure output identifies a GitHub request; it requires isolating the failed step and keeps certificate checks intact.

Protected Git preflight recognises explicit `git apply --cached` and `--index` writes, literal patch paths, stdin, and supported Git inspection/staging chains. Standalone `--check` without `--apply` remains on its existing route, including cached/index checks; a supported check-then-apply chain is stopped before any stage launches because of its later writer. Literal pipelines ending in an eligible apply are recognised for capability detection, with supported Git inspections, `cat`, `printf`, and literal `python`/`python3 -c` producers. This does not certify producer scripts as read-only or safe: the whole invocation remains subject to existing review. Unsupported options (including report-only modes and implicit-index `--3way`), repository/environment overrides, wrappers, substitutions and redirections stay outside this extension. A preflight stop means no command payload launched and no automatic native retry is authorised. For inline patches, the result returns `command_template`, bounded `inline_files` identity metadata, and instructions to resubmit the template with the original `files` payload and `require_escalated`. Temporary materialised paths are cleaned up and must not be replayed. An edited command without a faithfully reusable template requires a new explicit invocation rather than restoring the original command.

Sandbox startup cancellation is retained during asynchronous filesystem preparation. A terminate request, closed command input or helper shutdown received at this stage cancels before runtime initialization and payload launch; it does not relax validation or authorise replay.

Sandbox helper failures return `sandbox_helper_failed`, a bounded failure category, `terminal_id`, `command_id`, and known launch evidence. Before readiness, launch state stays `unknown`; after readiness it stays `true`, but neither establishes the command's outcome. Retained output is included as a bounded preview with retention metadata. Use both IDs with `get_terminal_output` before deciding what to do next; no automatic replay is offered. Missing protected files remain write-denied, and later presence or content changes still invalidate their integrity snapshot. Command audit events record human approval requests before waiting and responses separately, excluding coordinator-only decisions and cancelled preflight.

`sandbox_protected_root_drift` identifies a protected snapshot change before launch, with a bounded relative path and change category. Inspect the change and request a newly prepared execution; repeated drift needs the concurrent host mutation resolved, not native bypass. A symbolic-link lock under shared `.git/worktrees/<name>/` metadata may belong to a live process: preserve it, inspect ownership, and use the separately reviewed native option when offered rather than deleting the lock. Hard links and other unexpected nodes retain their inspection/repair guidance.

Normal macOS sandbox launches preserve host `HOME` and use a private per-command npm/npx cache, including commands invoked through task wrappers. Case-insensitive per-command `env` aliases for `npm_config_cache` win; equal aliases collapse to one canonical `npm_config_cache`, while conflicting values fail before launch with `sandbox_preparation_failed` and `conflicting_npm_cache_overrides`. An equally empty alias set uses sandbox storage, matching npm's unset-value handling. Otherwise sandbox storage replaces inherited and shell-policy cache variables in any case and overrides `.npmrc` cache settings only. The selected cache entry is protected from environment-budget eviction. Registry, authentication and toolchain trust settings are not copied or changed. npm's explicit CLI `--cache` still wins, but neither a CLI nor an environment override grants write access to its target. Caches are cold and removed after the command's process tree finishes, so repeated downloads and existing destination approvals may remain necessary. Result metadata describes the cache source without exposing environment values. `temporary_home` remains an explicit disposable-HOME option, not npm cache recovery.

A remaining npm host-HOME cache denial can return `sandbox_npm_cache_write` guidance to inspect cache/log overrides, preserve HOME and request fresh review of the failed step after repair. AgentLink never silently rewrites CLI flags, auto-trusts mise/asdf, changes filesystem grants or automatically replays the command. For other host-HOME write failures, commands or failure output identifying credential-backed configuration, or commands resolving through mise/asdf shims on a known sandbox PATH, do not receive disposable-HOME suggestions. An unrelated shim directory on PATH alone is not enough evidence. The `temporary_home_unsuitable` field explains the limitation, and the failed step can receive a separate native review that preserves host configuration. AgentLink does not trust toolchain configuration automatically. Finalized Docker socket permission denials receive the same non-automatic native guidance in `execute_command` and `get_terminal_output`, including deferred and recently closed commands with matching execution context. Running, incomplete, read-only, deliberately killed, prompt-terminated, or inline-file-dependent commands do not receive replay suggestions.

Recognised GitHub TLS or Git SSH failures in a compound command return managed-network recovery guidance even when its final segment exits `0`. SSH detection includes authentication-method negotiation failures and `Connection closed by UNKNOWN port`, including commands using a remote alias such as `origin`. The final exit code is preserved; it does not prove each earlier step succeeded. The guidance explicitly leaves individual segment outcomes uncertain, asks you to identify and isolate the candidate network step, and never permits replaying successful prefixes or disabling TLS verification.

On macOS, sandboxed commands with network access can reach the system certificate trust service (`com.apple.trustd.agent`), so Go-based CLIs such as `gh`, `gcloud`, `terraform` and `kubectl` verify TLS normally inside the sandbox instead of failing with `x509: OSStatus -26276`. Commands without network access keep that service blocked. Certificate verification is never disabled.

Recognised Go dependency-download TLS failures (including `proxy.golang.org` certificate errors during `go test`) return `managed_network_tls_trust` guidance on the sandbox route. The underlying trust cause remains undetermined. Inspect partial changes and test output before choosing an exact separately reviewed retry: snapshot-updating tests may already have written files. Go recovery never offers blind same-command replay or disables certificate verification.

A sandboxed direct `swift build` or `swift test` whose output shows SwiftPM's nested manifest sandbox failing (`sandbox-exec: sandbox_apply: Operation not permitted`) returns `sandbox_swiftpm_nested_sandbox` guidance. It offers the exact command with `--disable-sandbox` added, using `sandbox_permissions: "require_managed_network"` so the retry stays inside AgentLink's sandbox (keep Approve for Me enabled), and keeps `temporary_home` if the original used it. Only SwiftPM's inner sandbox is disabled; the guidance never suggests native escalation and is never run automatically. Compound, env-prefixed, substituted, already `--disable-sandbox`, native, timed-out and ordinary compiler failures do not receive it.

A managed `curl` exit 28 with reported HTTP status `000`, zero connection time and zero TLS-handshake time returns `managed_network_connect_timeout` and bounded evidence. This distinguishes an unestablished connection from a response delay without claiming the proxy is at fault. Inspect managed connectivity or request a separately approved native connectivity diagnostic; do not replay mutating requests blindly or disable TLS checks.

Read-only command profiles recognise bounded Git branch queries, including `git branch --all --contains HEAD`, optional reference filters, sort/format values, and explicit `--list` patterns. Branch creation, deletion, renaming, copying, upstream changes and unknown options remain rejected; query recognition does not grant network or write access.

Output-filter checks distinguish balanced `$()` command substitutions used to compute arguments or select inputs from visible terminal pipelines. For example, `files=$(list | head -3)` is not an output-filter violation, while `command | head -3` still requires `output_head`. Nested or quoted substitutions preserve this distinction; unresolved syntax remains conservative. File-write checks and command approval still apply.

Exact command-tool parameters: [terminal tools](complete-reference.md#execute_command).

### Ask Agent scratch folder (Desktop and Browser Ask Agent)

Each Ask Agent chat in Desktop (and the Browser Ask Agent served by the same helper) has a private scratch folder at `~/.agentlink/ask-agent-sandboxes/<chat>/work`. It lets the agent analyse data, convert files and make charts without a project:

- `execute_command` runs a non-interactive command in the scratch folder through the sandbox (Seatbelt on macOS, bubblewrap on Linux; the shell is zsh on macOS and bash on Linux). Commands can write only inside that chat's folder, cannot read your home folder or other chats, and have no network access, so `pip install` and similar installs fail. Background commands run only in granted folders (see below); `timeoutMs` defaults to 120 seconds (maximum 10 minutes). The parameters follow the standalone CLI's command tools rather than VS Code's terminal tools. No approval is asked because the sandbox is the boundary.
- `get_command_output` reads a previous command's output by `commandId`.
- `write_file` creates or replaces a file in the scratch folder (up to 5 MiB per write, 1 GiB per chat). It cannot write anywhere else or through links.
- `present_files` gives you files from the scratch folder: PNG, JPEG, GIF and WebP images show inline, and other files (CSV, PDF, Markdown and so on) appear as file chips with a download button. Up to 10 files, 8 MiB each and 20 MiB per call.
- `read_file`, `list_files` and `search_files` also read the scratch folder; relative paths resolve inside it.

Files you attach to the chat are copied into `inputs/`. Deleting the chat deletes its folder. On Linux (Desktop and the Browser Ask Agent) the tools are offered only when the host passes the same bubblewrap check as the VS Code sandbox (see [Linux command sandbox](capabilities.md#linux-command-sandbox)). The check runs once per browser gateway helper process, so after fixing the host restart the helper (for example by quitting every VS Code window). Ripgrep defaults to `/usr/bin/rg`; set `AGENTLINK_SANDBOX_RIPGREP_PATH` to use another one. The tools are not offered on Windows, or when the packaged sandbox helper is missing. The scratch folder cannot touch your projects or run with your normal permissions; to work in a project, grant it for commands (below).

### Ask Agent commands in granted folders

Usually the agent asks for the folder it needs (see [Agent-requested folder access](#agent-requested-folder-access) below). You can also grant one yourself: open **Manage access** (in Desktop's **⋯** menu at the top right of the chat; the folder button in the browser's Ask Agent header), choose **Add a folder yourself**, enter a path (`~/` works) and, when the scratch folder is available, tick **Also allow commands and edits in this folder (asks first)**. The result shows inside the panel. The agent then sees the folder listed in its instructions and can run `execute_command` with `cwd` set to an absolute path inside it:

- Unless a rule or Approve for Me decides it, a command shows a **Run a terminal command** card with **Run**, an editable command and **Reject**, on any signed-in client including a paired phone. Nothing runs until you approve; an edited command runs as you wrote it.
- The card has a rule row per sub-command, like VS Code's command card: **Allow**, **Prompt** or **Forbidden**, matched as a prefix, exact command or regex, with scope **Session** (this chat, until the helper restarts or the chat is deleted), **Project** (this granted folder) or **Global** (every granted folder). **Save Rules & Run** saves them; Project and Global rules are kept in `~/.agentlink/ask-agent-command-policy.json`. Matching follows VS Code: every part of a compound command must be allowed to skip the card, Forbidden beats Prompt beats Allow, and a Forbidden match refuses the command without a card (the tool result has `status: "forbidden"`). Ask Agent keeps its own rules and does not use VS Code's.
- **Approve for Me** (the shield toggle in the composer toolbar, as in VS Code, and also in Manage access once a folder allows commands) runs commands and file edits in granted folders without a card. Turning it on while a command or edit card is open approves that card if Approve for Me would have let it through. They still run in the sandbox, Prompt rules still show the card, and Forbidden rules still refuse. The setting is saved in the same file.
- Saving rules and turning Approve for Me on work only from Desktop or a browser on the same computer; a paired LAN or phone client gets `command_rules_require_this_machine` or `command_policy_requires_this_machine` and can still choose **Run**. Any client can turn Approve for Me off or remove a saved rule from the panel.
- Commands run in the same sandbox as the scratch folder, with a wider boundary: they can read files on this computer, can write only inside the granted folder and temporary folders, and cannot change the folder's top-level Git metadata or agent instruction files. By default they cannot reach the internet, so `npm install`, `git fetch` or `git push` fail. On macOS they can still connect to services running on this computer and can listen on a local port, so a dev or test server runs in the sandbox and opens in your browser (the card says so; Seatbelt cannot limit the listener to loopback addresses). On Linux each command has its own network namespace and no network at all: a server it starts is reachable only from inside that command, not from your browser. They get your login shell's `PATH` and environment, minus variables whose names look like secrets (for example containing `KEY`, `SECRET` or `TOKEN`) and the helper's own variables.
- **Internet access.** The agent can pass `sandbox_permissions: "require_managed_network"` (with an optional `reason`) for a command that needs the internet. The command card then says **internet asks per destination**, and the command still runs in the sandbox, so rules and Approve for Me can approve it as usual. Each public destination it connects to pauses on a **Connect to a public network destination** card showing the host, port, resolved address, command and folder. **Allow Once** lets that one connection through; choosing **Session** (this chat), **Project** (this granted folder) or **Global** (every granted folder) and **Save Exact Rule & Allow** also allows that exact `protocol://host:port` later without a card. Project and Global destination rules are kept in `~/.agentlink/ask-agent-command-policy.json` and listed in the local access panel with **Remove**. Private network and cloud metadata addresses stay blocked. Destination cards are queued and shown one at a time. A destination that arrives while another kind of approval (such as a command card) is open is refused, and a card still open when its command exits or times out is withdrawn and allows nothing. Any client can allow once (the relay's generic approve action counts as Allow Once); saving a destination rule works only from this computer (others get `destination_rules_require_this_machine`).
- **Running outside the sandbox.** For something the sandbox blocks, the agent can pass `sandbox_permissions: "require_escalated"` with a `reason`. The command then runs as you with full access to files, credentials, network and local processes. It always shows a card labelled **Full terminal access** with no rule rows: saved Allow rules and Approve for Me never approve it, though a Forbidden rule still refuses it. Only Desktop or a browser on the same computer can choose **Run** or edit it; a paired LAN or phone client sees the card with **Approve on the computer running AgentLink** and can only reject (others get `unsandboxed_command_requires_this_machine`).
- `sandbox_permissions` works only for commands in a granted folder. Scratch-folder commands always run in the sandbox without internet and fail with `sandbox_permissions_need_granted_folder` if they ask for more.
- `get_command_output` reads their output like scratch-folder commands.
- **Background commands.** With `background: true` a command in a granted folder (a dev server, test watcher or watch build) starts and the tool call returns at once with its `commandId`. It keeps running after the agent replies, until it exits, reaches its `timeoutMs` (default 1 hour, maximum 8 hours; foreground commands keep the 10-minute maximum), the agent calls `stop_command`, or you revoke the folder or delete the chat. Stopping the turn does not stop it, and quitting the helper does. The command card says **Background** and shows the time limit; rules and Approve for Me decide it like any sandboxed command. A chat can run at most 5 background commands at once (`too_many_background_commands`). Background commands cannot use `require_managed_network` (`background_network_unavailable`) and are refused in the scratch folder (`background_needs_granted_folder`). `list_commands` lists the chat's commands and `stop_command` stops one; both, like `apply_diff`, are offered only while a folder is granted for commands.
- Grants can be added only from Desktop or a browser on the same computer (this now applies to read-only grants too; paired LAN and phone clients get `grant_requires_this_machine`). Commands can be granted only for a folder, not for the whole disk or your home folder, and only where the scratch-folder sandbox is available (otherwise `commands_unavailable`). Because the sandbox protects Git metadata and agent instruction files only at the top of the folder, a folder that contains other repositories (outside `node_modules`) is refused with `commands_grant_contains_repositories`; grant each repository's folder instead. A grant applies to the folder it was made for: if that path is later replaced with a symlink to somewhere else, commands there stop working until you grant it again. Any client can revoke a grant; revoking a commands grant, or re-granting the folder as read-only, stops its running commands and refuses new ones.
- Grants last until the browser gateway helper restarts.

#### Agent-requested folder access

When the scratch folder is available the agent also has `request_folder_access` (`path`, `access` `"commands"` (default) or `"read"`, a required `reason`, and `create`). It shows a write-style card with the folder, the reason and what the access allows, and approving adds the same grant as the panel, with the same checks. The agent is told to keep throwaway work in the scratch folder, to use an existing folder you mention, and otherwise to suggest a new folder under `~/AgentLink/<task-name>`.

- A new empty folder (`create: true`) can be created only inside your home folder (otherwise `create_outside_home`). For a new folder under `~/AgentLink/`, any signed-in client, including a paired phone, can choose **Create folder and allow**, since there is nothing in it yet. AgentLink creates it after approval. With Approve for Me on, such a folder is created and granted without a card, and turning Approve for Me on while its card is open approves it; existing folders and new folders elsewhere still ask.
- Access to an existing folder, or a new folder elsewhere in your home folder, can be approved only from Desktop or a browser on the same computer; other clients get `grant_requires_this_machine` and can only reject.
- A folder already covered by a grant returns `already_granted` without a card. A missing folder without `create: true` returns `path_not_found`, and a refused grant returns the same errors as the panel (for example `commands_grant_too_broad` or `commands_grant_contains_repositories`). Results are `granted` (with `created`), `rejected_by_user` (with any reason you typed), `cancelled` or `approval_pending`.
- Approving a folder for commands (`access: "commands"`) also lets the agent create and edit files there without a card, like Approve for Me for that folder only. Agent instruction and configuration files still ask, the other edit rules below still apply, and commands still follow rules and Approve for Me. Each folder in **Manage access** that allows commands has **Edit files without asking**, which any signed-in client can turn on or off; folders you add yourself start with it off.
- **Manage access** lists granted folders with their access and **Revoke**, then the command settings (Approve for Me, saved rules and network destinations). In Desktop it also has **Show scratch folder in Finder**, which opens this chat's scratch folder (only on the computer running AgentLink).

#### File edits in granted folders

The agent can also edit files in a folder granted for commands, without running a command:

- `read_file` on a file in such a folder returns a `contentHash` (SHA-256 of the file). It is left out when secrets in a settings file were hidden from the result, so a redacted copy can never be written back.
- `write_file` with an absolute path inside the folder creates a file (`expectedAbsent: true`) or replaces one (`expectedContentHash` from `read_file`). Relative paths still write to the scratch folder.
- `apply_diff` changes part of a file with SEARCH/REPLACE blocks against `expectedContentHash`. It is offered only while a folder is granted for commands.
- An edit whose file changed since it was read fails before any card, so the agent re-reads and tries again.
- Each edit shows a write card with the file path and diff (**Apply** or **Create**, or **Reject**). Any signed-in client can apply it. With Approve for Me on, ordinary edits apply without a card.
- Agent instruction and configuration files (for example `AGENTS.md`, `CLAUDE.md`, `.agentlink/` and `.claude/`) always show the card, even with Approve for Me, and only Desktop or a browser on the same computer can apply them; other clients get `protected_edit_requires_this_machine` and can only reject. Git metadata (`.git/`) and `.env` files cannot be edited.
- Settings files whose secrets `read_file` hides cannot be changed (`edit_refused_secrets`), so the real values are never overwritten or shown on a card. A change with more than 100,000 characters of diff is refused (`edit_too_large_to_review`) rather than approved from a partial view; the agent splits it into smaller edits. With Approve for Me on, ordinary edits of any size still apply.
- An edit waits for no command to be running that can write in that folder (`command_running`), background commands included and commands from an enclosing granted folder too, so the agent stops a dev server with `stop_command` before editing there. A command launched in an overlapping folder while an edit is being written fails with `edit_in_progress`. An edit fails with `path_changed` if the file's location changed while the card was open.
- Paths outside every granted folder, or the granted folder itself, fail with `path_not_granted`. Revoking the grant withdraws an open edit card, and a write already in progress finishes before the revoke completes.

`present_files` still works only in the scratch folder.

## Work with people and the session

- `ask_user` asks structured questions. Host-authenticated human answers in VS Code and mirrored browser workspace chat can inform Guardian review of the matching session. The host binds the literal question, options, answer and note to its request and tool call; agent-authored question text is context, not independent human instructions. Coordinator replies, relays to another session and arbitrary tool output cannot create human authority. Rules, risk review and approvals remain in force. While a question card is open, **Chat input** sets it aside so the composer works as the normal chat input (for example to run `/mcp`); the question stays pending with its selections and draft kept, and **Back to question** returns to it.
- When a human answer or message arrives while Guardian is reviewing an `execute_command` call, the command is reviewed again; if the approval is still stale when the terminal is about to dispatch, nothing is sent and the result has `status: "authorization_stale"`, `command_sent: false` and `retry_safe: true`. Human approvals and `rejected_by_user` results that follow an automatic review include a `prior_review` object (review ID, status, outcome, model) so the agent can see what Guardian decided first.
- `todo_write` maintains visible work state. Every item, including nested children, needs a non-blank `id`, `content`, and `activeForm` plus a `status`; the schema describes these inline for up to three nesting levels so provider conversions keep them visible. Items missing a required field are ignored, and the model-visible correction names the missing fields. The list changes only when the agent calls the tool, so multi-step work should update it at each real task transition.
- `set_task_status` ends a turn with a truthful result. Clicking its Continue or custom next-step button adds the full prompt to the composer for review and editing, rather than sending it. Existing draft text and attachments are preserved. This applies in VS Code and browser chat, including Ask Agent; the separate Auto Continue setting still sends automatically when enabled.
- In VS Code sessions, the final status card adds a **Work summary** when AgentLink's file tools changed files: one row per file (Created, Edited or Deleted, with line counts) that expands to a read-only diff, and a button to open the file. **Since previous summary** is the default; **Session so far** appears once there are earlier summaries. AgentLink builds the summary itself from the content each verified save left on disk (including format-on-save), not from the model's text, and freezes it, so later edits never change an earlier card. It is honest about what it can't see: a file changed by something else between AgentLink edits is marked **changed between edits** and shows each run of edits separately; a file that differed on disk from AgentLink's last edit when the summary was taken is marked **changed on disk after**; and notes say when shell commands, MCP tools or background agents ran (their changes aren't captured here) or when the session was reloaded (earlier changes aren't included). Large, binary or over-limit files show counts or metadata without a diff. Summaries are stored in the transcript; the browser and Desktop remote views load them on demand. The tool's inputs are unchanged.
- `switch_mode` changes the workflow mode.
- `search_session_history` and `read_session_excerpt` retrieve prior context when allowed. The standalone CLI and Assistant offer the same two tools, with the same descriptions, inputs and results, once a session has an earlier turn. They search the stored transcript from earlier turns, and have no `handoff_source` predecessor, so that scope reports it as unavailable.
- `search_workspace_sessions` and `read_workspace_session_excerpt` find earlier saved sessions in the same project, for "have we done this before?" or "why did we choose this?". Search uses a local lexical index (no embeddings or external calls), then re-reads each matching session before returning bounded excerpts, so deleted or changed sessions never leak through a stale index. Results report index coverage; while backfill is incomplete, no match does not prove a topic was never discussed. The current session, background agents and other projects are excluded. Set `include_worktrees: true` to also search other git worktrees of the same repository; their history is read without being modified, and matches show the worktree as `origin`. These tools are offered only to foreground VS Code sessions with saved history, are not exempt from skill `allowed-tools`, and are absent from bounded review, research, `/btw` and worktree-setup profiles. The CLI, Assistant and Ask Agent do not offer them yet; SDK hosts can compose `@agentlink/core/workspace-session-history` with their own session source and index.

In native background sessions, `set_task_status.result` advertises the accepted coordinator-facing envelopes: `text` requires `text`; `patch` requires `summary` and `files` (not `changedFiles`); `verification` requires `passed` and `summary`; `review_findings` requires `findings`. An expected review completion also requires `emptyDiff`. When no result type was delegated, the schema exposes all four alternatives. File paths, screenshot paths, and finding paths must be non-empty workspace-relative paths without `..` segments, and finding line numbers must be positive integers. Invalid envelopes return up to eight field-specific `issues` without echoing submitted content, and do not finalise the session or complete TODOs. Legacy extra fields remain compatible, but cannot replace required fields. Completed text results must be non-blank; interrupted tasks may omit a result.

Exact session-tool parameters: [orchestration tools](complete-reference.md#built-in-agent-orchestration-tools).

## Delegate work

For native writable debugging, use `mode: "code"` or `taskClass: "debug"` with non-empty `ownedPaths`. The latter defaults to Code only from a Code-mode parent, when no explicit mode or review-only permission profile prevents it. Unscoped Debug remains investigative; foreground modes and ACP defaults are unchanged. Other mode/profile/skill/ownership restrictions still apply.

- `spawn_background_agent` starts a bounded background task. `modelTier` accepts `cheap`, `balanced`, `deep_reasoning`, or `foreground`; research defaults to the foreground model's tier, and other ordinary native work defaults below the foreground model when a configured tier group can satisfy it.
- `get_background_status`, `get_background_result`, `steer_background_agent`, and `kill_background_agent` supervise it. `get_background_result` keeps its single-session form and also accepts `sessionIds` with `return_when: "any" | "all"` for one cleanup-safe bounded wait across several agents.
- Fleet workflows can run structured review, browser verification, best-of-N work, or scheduled goals.

Orchestrate mode is the coordination-first workflow for delegating substantial research, codebase reading, implementation, validation, and review while keeping the frontier foreground model's context small. It chooses the lowest sufficient model tier, assigns non-overlapping writable scopes, monitors without tight polling, and integrates compact results rather than repeating each agent's investigation.

Use clear ownership and a focused review scope for writable or review work. `ownedPaths` restrict a child's writes; they never grant access. A native writable child can only write outside the workspace roots with path trust and write approval inherited from its parent, because it cannot request them itself. If no inherited rule can reach an outside owned path, `spawn_background_agent` rejects the spawn immediately with the missing authority and recovery options (add the folder to the workspace, make the edits in the foreground, or grant trust and a write rule first). If only narrower rules exist beneath it, the spawn succeeds with `writeScopeWarnings`. Read-only delegations and in-workspace scopes are not checked, and dispatch-time enforcement is unchanged. Structured `ownedPaths`/`forbiddenPaths` are included verbatim in the child's task handoff when supplied. Native agents are told these are enforced path restrictions; ACP agents are told they are advisory. Forbidden paths take precedence, and steering or coordinator replies cannot expand the configured scope. Delegate a new scope or let the coordinator handle extra files instead. Native text and structured reviews receive bounded finalization recovery after an output limit or missing result. Empty text and unfinalized native review output are incomplete, not successful; partial output remains available. Explicit unsuccessful provider/ACP stops cannot turn partial output into a completed review. See [background agents](capabilities.md#background-agents-and-orchestration) and the [full background tool reference](complete-reference.md#spawn_background_agent).

`respond_to_background_question` returns `ownershipChanged: false`: an accepted answer resolves the question but cannot expand native write ownership. The coordinator must handle additional paths or spawn a replacement. The same reminder is included with coordinator question interjections.

## Connect external capabilities

- `find_mcp_tools` and `call_mcp_tool` discover and invoke configured MCP capabilities. In VS Code workspace sessions, discovery marks server-annotated read-only tools `read_only: true`; only those can run inside `compose`. In the CLI, untargeted discovery lists servers needing sign-in without connecting them; specifying a server connects only that server, and `call_mcp_tool` can invoke its tools in the same turn under the normal approval policy.
- In VS Code-backed sessions and standalone Desktop, `find_mcp_tools` also reports configured-server connection status and startup diagnostics. A named failed server returns an error explaining why it has no tools; an untargeted search includes server statuses without initiating unrelated sign-in. Failed servers remain in the agent catalog. Paused startup/auth failures are not repeatedly reconnected by discovery.
- In VS Code-backed **Approve for Me** sessions, MCP tool calls without existing approval go through Guardian for a one-shot allow or deny. The optional TypeSafe Jev first pass can allow complete, non-sensitive calls when authorization, task relevance, safety and bounded-impact probabilities meet the configured threshold; other calls receive full Guardian review. A Guardian denial opens the normal human approval card with its explanation and the call arguments, rather than returning an immediate error. Execution still requires an explicit human allow; human rejection, cancellation and hard tool restrictions remain enforced. Unavailable review also retains human fallback. When the human rejects an escalated denial, `guardian_rationale` preserves the Guardian explanation in the tool result alongside any human rejection reason or follow-up. No automated decision saves a tool/server rule, and compose still requires existing approval. See [MCP approval behaviour](mcp.md).
- Resources and prompts use `list_mcp_resources`, `read_mcp_resource`, `list_mcp_prompts`, and `get_mcp_prompt`. In VS Code-backed sessions these four are deferred: discover them with `find_native_tools` and call them through `call_native_tool` (or directly by exact name). `find_mcp_tools` and `call_mcp_tool` stay directly available.
- Native `web_search` and `web_fetch` may be available according to the configured web-access backend. Models whose provider has no hosted web borrow the ChatGPT/Codex OAuth standalone route when you are signed in to Codex. Agents try these native tools first and fall back to MCP web tools when they fail or return too little.
- The standalone CLI and the Assistant offer their own `web_fetch` (`url`, `max_length`, `start_index`) and `web_search` (`query`, `max_results`, `time_range`, `language`). Search uses Codex hosted search for Codex models and a configured SearXNG for others. The CLI reads only public sites directly from the machine ([Standalone CLI](standalone-cli.md#web-tools)); the Assistant follows each project's network preset.

Native `review` and `readonly-research` profiles expose these public-web tools only when supported by the selected provider (or a borrowed Codex OAuth route) and enabled by current web policy. Active skill restrictions still apply. This does not authorise shell network access, credential-backed GitHub reads, or arbitrary `gh`/`curl` commands. When no supported web transport is available, fetch the material in the foreground and pass a local artifact to the child.

A Codex OAuth `web_fetch` can follow the provider's line-addressed continuation. The provider page window is sized from the retention budget (`agentlink.webAccess.maxFetchContentTokens`, capped at 16,384 tokens), not from `max_length`, so a small inline preview still retrieves the whole page when it fits. The VS Code host keeps the inline result bounded and returns an AgentLink temp `output_file` for additional retained content; read it with `read_file` rather than repeating the fetch. If the provider still has more than AgentLink retained, continue from `next_start_line` with `start_line`. Browser Ask Agent does not expose host temp-file paths. An explicit `start_line` selects a page-open request even when `find` is supplied. Without `find`, its inline preview starts at the first returned numbered line at or after `start_line`, before applying `max_length`; earlier provider headers and navigation do not consume the preview budget or count as truncation. Retained output still preserves the original provider content. Find-only reads can continue through navigation-only pages within existing limits, then preview the matching numbered source content while retaining the original pages. If the provider ignores the initial requested line or cannot reach the requested match before stalling or exhausting those limits, page access fails with `provider_page_focus_unavailable` so the existing hosted fallback can recover; navigation is not returned as a successful focused read. Continuation is based on returned line numbers, not the requested offset. Overlapping continuation pages retain only new line blocks. Unfocused reads that stall on a continuation retain earlier content with truncation and `output_warning`, and omit `next_start_line` rather than inviting a repeat loop.

A Codex page-access response consisting of the provider's `Internal Error ()` marker (with optional provider or citation-prefixed `Source: open(...)` headers and provider `Failed to fetch <url>: <reason>` lines, such as `Cache miss`) is a failed read, not successful page content. Existing hosted fallback may recover an initial failure; otherwise the error names `provider_page_internal_error` and advises retrying the read or using another approved web transport. If only a continuation page fails, earlier content is retained with truncation/pagination-warning metadata, without appending the error text or claiming completion. An article that merely discusses the error is not rejected.

Codex hosted web requests use the normal Responses body and headers, including for OAuth models whose ordinary agent turns use Responses Lite. A Lite preference does not disable hosted fallback. Standalone page-access failures can therefore fall back to the selected model's hosted web search, which can also open pages, without changing models. The VS Code agent and browser Ask Agent use the same routing rule; ordinary turns without hosted tools retain their existing request format. Web policy, domain filters, approvals, and provider availability still apply.

MCP configuration and trust behavior: [MCP](mcp.md). Exact native web contracts: [web access](complete-reference.md#web-access).

## Inspect authorization provenance

In development builds, VS Code-backed sessions (including mirrored browser workspace chat) can use `diagnose_activity` to inspect host-recorded `authorizationAudit` on MCP call and managed-network `execute_command` evidence. Filter by `tool_name` or `tool_call_id` to distinguish an existing MCP grant, a destination rule, human approval, first-pass review, full Guardian review, or a host-policy rejection. Unknown reviewer sources stay `unknown`; older activity has no audit field.

Each audit retains at most 20 decisions plus `omittedCount`. Records contain only action family, approval basis, allow/deny decision, status, and reviewer/model identifiers and reviewed risk/authorization levels when known. They never include arguments, destinations, hosts, URLs, credentials, or raw rationale, and MCP result JSON cannot supply this evidence. A reviewed allow is separate from final authorization, so a later policy change can invalidate it. An execution error after approval does not mean authorization was denied.

Coverage is a snapshot when the tool returns: later sockets from background, timed-out, or detached commands are still approved normally but are not added to that completed tool's diagnostic evidence. Host-blocked connections that never reach destination review and MCP calls inside Compose do not acquire separate audit entries. Projectless helper-owned Ask Agent and standalone CLI do not expose this VS Code activity diagnostic path; do not infer approval provenance from its absence there.

## Report bugs and self-improvement opportunities in development builds

`send_feedback` helps AgentLink improve itself by collecting concrete bugs, workflow improvements, and feature requests grounded in actual use. Successful tasks can reveal unnecessary steps or missing capabilities too. Use the affected native tool name, or `tool_name: "agentlink"` for a cross-tool or general AgentLink workflow. Do not submit routine praise, generic wishlists, or third-party MCP-server defects; suggestions do not authorize self-modification or weaker safeguards.

New reports require a non-empty `observed_impact` describing an observed task consequence or unmet need. Preserve bug inputs, results, reproduction details, recovery, and recurrence; a bug report never needs a diagnosis or solution. Optional `category` is `bug`, `improvement`, or `feature_request`. Optional `suspected_cause` separates an unverified diagnosis from the evidence, and `suggested_change` captures a proposed fix, workflow improvement, or new capability. `workaround`, `observed_recurrence`, and `improvement_signal` capture recovery/outcome, occurrences actually observed, and a proposed observable success check. Report evidence, not importance scores, guessed prevalence, or invented savings. Reporting has no quota and must not derail the user's task.

`get_feedback` returns these fields when recorded. Older records remain readable without inferred categories or causes, with unchanged IDs and triage/deletion metadata. Every field of a report up to 128 KiB is preserved; larger reports are rejected unrecorded with per-field sizes. Queue listings stay bounded to 4,000 UTF-8 bytes per entry, so long reports appear as previews (`content_status: "preview"`, with hypothesis and proposal text shortened before bug evidence) and the sidebar labels them. The send acknowledgement lists any `truncated_fields`. Call `get_feedback` with only `id` to read the complete report: small reports return a parsed `entry`, larger ones return bounded `record_json` pages with an exact `next_request`. If full content is unavailable, the error labels the retained preview as partial. Older entries report `legacy_unverified`, and text discarded by earlier versions cannot be recovered. An `unknown` send result means the write could not be confirmed: look up the ID before resubmitting.

Validate bug evidence independently of the proposed fix. Review improvement/feature candidates against observed need, alternatives, product fit, and safety constraints without requiring a failing test. Before asking for approval, give the triaging AI's own verdict (worth pursuing, simplify, investigate first, or decline), practical value versus implementation and maintenance complexity, gimmick risk, overlap with existing capabilities, simpler alternatives (including no change), and an evidence-backed recommendation with uncertainty stated. Include grounded proposals you recommend declining, not only endorsements. Put this assessment in each approval question's context so the user can make an informed decision; do not merely ask for the user's thoughts. Backlog approval is not implementation permission. Deferred proposals remain active and untriaged, and useful P2/P3 improvements are not discarded merely for being lower priority. This is triage workflow guidance, not a new tool-enforced approval gate. The development sidebar shows supplied categories and separate expandable evidence, hypotheses, proposals, and success checks, all searchable. Exact contracts: [development feedback tools](complete-reference.md#development-feedback-tools).
