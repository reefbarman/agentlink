# AgentLink Tools Reference

This guide explains the built-in agent's tool families and points to the complete parameter reference. Tools are available only when the current mode, active skill, session type, and approval policy allow them.

## Read and understand a workspace

Use the lightweight orientation tools before broad changes:

- `read_file` with `view: "context"` — read an oriented file slice with metadata, diagnostics, symbols, and working-set status.
- `read_file` (default `view: "content"`) — read exact content, a bounded range, local images, or extracted PDF text.
- `list_files` — explore paths; `search_files` — search exact text or find code by intent.
- `get_repo_map` and `get_module_neighbors` — understand structure and dependency impact. JavaScript/TypeScript links resolve nearest `tsconfig.json`/`jsconfig.json` `paths` and `baseUrl`, including JSONC, exact/one-wildcard mappings, ordered fallbacks, and workspace-contained `extends` chains. Alias targets are checked against the canonical workspace boundary, including symlinks. Existing stored bare imports are resolved again when loading a map, so config-only changes refresh displayed links and reverse dependents.
- Language tools — definitions, references, symbols, hovers, code actions, and rename support through VS Code.

**Indexed tools are workspace-only.** `get_repo_map`, `get_module_neighbors`, and query-mode `search_files` only cover files/folders within the current workspace folders. An absolute path to an external repository does not make its index available, even if it is open in another window or was previously indexed. `get_repo_map.include_external` includes dependency names, not external repository contents.

Use `search_files` with `query` for ranked code search when you do not know the location or exact wording, and with `regex` when you know the text or pattern. Exactly one of these inputs is required; both or neither is invalid. Query mode requires an explicit file or directory `path`, defaults `max_results` to 10, and accepts `exclude_globs`; regex mode defaults `max_results` to 300. Query limits are clamped to integers from 1 to 300. Query mode ignores regex-specific options with a warning, and `exclude_globs` is query-only (supplying it to regex mode produces a warning). External paths support regex search, `read_file`, and `list_files` subject to existing path permissions and approvals. `read_file` uses anchors or offsets to locate content in a known file, and `list_files` lists paths without a query mode.

Successful query results report the ranking actually used (`hybrid`, `lexical`, or `keyword_fallback`) and a bounded `ranking_reason` when applicable. Fallback results include repair guidance for the reported embedding or index category without exposing raw provider error bodies. Adjacent query terms and joined camel/Pascal-case identifiers boost indexed and keyword-fallback matches; snapshot and fixture paths are downweighted, not excluded. `embeddings_disabled` is intentional lexical operation, not a failure. Browser workspace chat mirrors native search; projectless Browser Ask Agent remains regex-only and has no workspace index.

In VS Code workspace sessions and mirrored browser workspace chat, `read_file` is one tool with two views. `view` is optional and defaults to `"content"`; omitting it never switches to the context view. Each view keeps the safety rules, path approvals, Compose limits, and result budget of the reader it replaced, and options belonging to the other view are rejected before the file is read. When a mode, profile, or skill allows only one view, the advertised schema lists only that view, and a context-only grant requires an explicit `view: "context"`. The former `get_context` tool no longer exists there; a call to it is rejected like any other unavailable tool. Older transcripts still show recorded `get_context` calls with their file link, grouped with other calls. The standalone CLI and projectless Browser Ask Agent keep their existing reader tools.

`anchor`, `anchor_regex`, and `anchor_offset` require `view: "content"` (or the default view). For `view: "context"`, select the starting line with numeric `offset`; anchor options are rejected before reading. `include_symbols` remains available in both views.

Set `include_symbols: false` in either `read_file` view to skip symbol lookup and omit the outline. The default remains true. This does not change diagnostics, content pagination, or unchanged-content deduplication. The context view bounds its symbol outline independently of the content slice: at most 60 entries and 6,000 UTF-8 bytes of serialized symbol JSON. Symbols starting within the requested lines are prioritised, then remaining space provides a whole-file overview. `symbols_truncated` and `symbols_omitted` indicate entries omitted from the supplied outline; use `get_symbols` for a fuller language-service view.

Context-view content is capped at 2,000 UTF-16 characters per source line and 20,000 characters total (including line numbers). Very long or minified files therefore stay bounded even with a small line count. `content_truncation` reports omitted UTF-8 bytes, wholly omitted lines, and `next_read` arguments for the first omitted position. Pass those arguments back to `read_file` to continue within a long line. `character_offset` is a zero-based UTF-16 offset in the starting line, applied after secret redaction; explicit character pages bypass line-based unchanged-content omission. The default content view retains its exact-read behaviour.

Regex `search_files`, indexed query excerpts, and keyword fallback apply the same narrow structured-settings redaction as file reads, including context and multiline values; malformed or unreadable eligible configuration is withheld. This does not detect arbitrary secrets in source files. Query excerpts are bounded to 4,000 source characters per result plus a truncation marker, with truncation counts. Recursive `list_files` honours an explicit root inside `node_modules` while still excluding nested dependency and Git metadata directories. Broken symlinks, permission-denied paths, and filesystem loops return bounded traversal warnings alongside discovered entries, including an empty pattern result. Such a listing is incomplete, not proof that the unreadable paths contain no matches. Invalid ripgrep arguments and process launch failures still return errors.

Exact parameters: [read and language tools](complete-reference.md#tools).

## Recover unsaved editor changes

VS Code workspace agents can use `get_editor_state` to inspect an already-open file-backed editor, including unsaved text that disk reads do not return. It supports disk files and buffers up to 8 MiB, with bounded line-numbered text and disk-to-buffer differences, the editor version, and separate whole-snapshot SHA-256 hashes for disk and buffer. `offset` and `limit` page buffer lines (maximum 200); each text preview is capped at 16,000 characters. Diff computation is bounded too: if it exceeds its work/time budget, `diff_omitted_reason: "computation_limit"` replaces the diff, while the inspected lines and hashes remain available. Eligible structured configuration secrets are redacted before either preview is produced.

Reviewed edits check the target document identity before changing its buffer and before an exact save. After a save failure, recovery guidance recommends `get_editor_state`/`save_editor` only when the same retained buffer is an open file-backed target within the recovery size limits. Otherwise it directs you to inspect and reconcile the preserved buffer in VS Code rather than repeat the patch against unchanged disk content. Restoring a previously active editor does not imply the retained document was discarded.

`save_editor` requires the inspected `path`, `editor_version`, `editor_hash`, and `disk_hash` (null only when the file is absent). It always asks for one-shot human approval, even with Approve for Me, and saves the existing buffer without formatting or ordinary save participants. The approval explicitly identifies that policy; check any required formatting separately afterwards. It does not replace or revert buffer content, persist trust, or apply a new patch. Refusal leaves unsaved work intact; changed disk/buffer state requires fresh inspection. A clean buffer already matching disk returns `already_saved`.

Files/buffers above 8 MiB, complete save approval text above 16,000 characters, and protected instruction/memory targets require the owning native workflow. A computation-limited save diff returns `editor_approval_diff_unavailable` without approval or saving; an oversized approval returns `editor_approval_too_large`. A truncated inspection diff is never sufficient to approve a save: the complete diff must fit the approval limit. Configuration whose inspection needs secret redaction or content withholding must be saved privately in VS Code, so raw secrets do not enter approval history. These tools require the VS Code editor host and are not provided by standalone CLI or helper-owned Ask Agent. Browser workspace supervision receives the existing approval events, but gains no editor mutation endpoint and its diff view stays read-only.

## Discover deferred native tools

Most AgentLink tools in the current request are exposed directly and must be called by name. `find_native_tools` searches only the compact deferred catalog named in its description; it is not a general availability check. When an exact query names tools that are already direct, or known native tools excluded from the current request, the result identifies those names and explains the next step. A tool can be present in one request and excluded from the next when the mode, active skill, background profile, or surface changes the authorized tool set.

Discovery and invocation guidance filter the captured catalog through the request's active allowance. A mode-blocked tool is reported as unavailable, not eligible, even when its definition remains in the cache-stable provider catalog. Calling an authorised direct tool through `call_native_tool` explains the direct route; excluded or dormant tools are not described as merely awaiting discovery. Command-validation recovery recommends file readers only when the current request authorises them. A restrictive skill may leave no callable read alternative: that restriction is reported rather than suggesting a prohibited reader or a policy bypass. None of this changes command rejection rules or widens permissions.

`get_module_neighbors` and the advanced fleet controls (`start_fleet_workflow`, `get_fleet_workflow_result`, `schedule_fleet_workflow`, `manage_fleet_automations`, and `detach_background_agent`) are deferred rather than included as full inline definitions. Discover the exact name with `find_native_tools`, then invoke it through `call_native_tool` using the returned schema. Existing mode, profile, skill, ownership, and approval restrictions still apply. Ordinary spawning and background supervision remain directly exposed when authorised.

## Load session skills and rules

`load_skill` remains available in restricted native profiles, including review and read-only research. `load_rule` is exposed only when the current request advertises deferred local rules, including in those restricted profiles; an empty rule catalog omits the tool entirely. These loaders read only artifacts authorised by the current session catalog, not arbitrary files. Enabled skills omitted from the bounded prompt projection remain loadable by their canonical paths. Skill content and real-path revision checks still apply.

When a skill path is rejected, `skill_not_in_catalog` returns up to ten catalog candidates matching the requested skill name or identity, plus an omitted count. This lookup reads no skill content and activates nothing. Retry with the intended candidate's exact path. If none match, refresh the catalog or check the skill's enabled state and mode. A valid advertised symlink alias returns the canonical activation path so its restrictions are applied consistently.

## Reduce related read-only fan-out

`compose` is a default-on foreground tool for known workflows with roughly four or more related reads. It runs a bounded JavaScript function body that calls authorized read-only tools, keeps child results out of provider history, and returns only the filtered, projected, joined, counted, or summarized JSON the model needs.

Compose is inline by default in workspace-backed foreground sessions whose mode and active skill permit it; no `find_native_tools` call is needed. Set the machine-scoped `agentlink.compose.enabled` setting to `false` to opt out, and reload affected VS Code windows after changing it. It remains unavailable to background agents, `/btw`, ACP, worktree setup, and projectless sessions. `AGENTLINK_DISABLE_COMPOSE=1` before startup force-disables it for recovery.

Use direct or ordinary parallel calls for one-offs, independent full results, and exploration where each result determines the next action. Compose cannot write, run commands, use MCP/web/memory/UI tools, nest itself, or open an approval. Text and extracted-PDF `read_file` calls are composable only without `query`; media/document output is rejected.

For independent reads, prefer `toolAllSettled`: it retains useful siblings when a file is missing or a child path needs interactive approval. A path-approval error returns `interaction_denied` with guidance to call that read tool directly; compose cannot obtain approval itself. Request, mode, skill, input and other policy violations remain fatal. Preserve per-child errors in the reduced summary. Reserve `toolAll` for batches where every result is required; it deliberately fails fast. Use paths established by prior reads/searches rather than guessed filenames. Child shapes differ: `search_files.results` is formatted text, not an array; `list_files.entries` is newline-separated text with paths relative to the requested directory, so split it, discard empty entries and prefix the directory before reading files. Syntax errors report bounded, script-relative line and column locations.

Compose cards in VS Code and browser workspace chat distinguish succeeded, failed, and cancelled children. Child errors wrap below the affected read instead of disrupting row alignment. The script is readable JavaScript under **Script**; failed results show the error first, with raw JSON and stack traces under **Technical details**.

The final output limit is 40 KiB. If exact secure retention succeeds, oversized output returns completed-with-spill metadata (`outputSpilled: true`) and a bounded preview plus `recovery.output_file`, rather than an execution failure. Read only needed artifact records instead of rerunning completed work. Retention failures and genuine execution errors remain errors; cancellation remains cancellation. Byte limits are unchanged.

Exact script helpers, child constraints, limits, and recovery behavior: [compose](complete-reference.md#compose).

## Make reviewed changes

- `write_file` creates or replaces a file through the reviewed editor save boundary.
- `apply_diff` applies reviewed search/replace blocks or unified diff hunks. Tool-description renderers may prefix examples with `//`; those prefixes are documentation comments, not part of the diff string. Send marker lines without `//`, while preserving comments that belong to the actual search/replacement payload. The first SEARCH opener or unified hunk header selects the format: `@@` hunk headers inside SEARCH/REPLACE blocks are literal payload, so patch files can be edited without switching to `write_file`. Properly prefixed reserved markers inside unified hunks remain payload too.
- `find_and_replace` makes a bounded multi-file replacement proposal. In regex mode, `$1` through `$99` refer to captures and `$$` emits a literal dollar. Nonexistent capture references and `$0` stay literal; existing unmatched optional captures become empty. Two-digit references fall back to the first capture digit when needed. Other dollar tokens stay literal. With regex off, replacement text is always literal.
- `rename_symbol` uses VS Code language intelligence where available.

`propose_memory` is the explicitly approved workflow for authoritative instructions, skills, and commands. For a project skill, set `skill_directory: ".agents/skills"` to propose a team-shareable `SKILL.md` instead of the default `.agentlink/skills`. The selector is valid only for `tier: "skill"`, `scope: "project"`; global proposals and projectless Browser Ask Agent cannot use it. Add/update/remove targets the selected directory exactly, without searching another same-named skill. Update/remove of a missing target fails rather than creating or silently removing anything. Normal review and verified-save boundaries still apply; see [authoritative configuration](customization.md#reviewed-authoritative-configuration).

In VS Code, automatic write/edit review opens, saves, and tab cleanup preserve keyboard focus so they do not interrupt typing in chat. Save without Formatting (including exact-preservation saves for Unity files) makes the target editor active without requesting keyboard focus, and preserves focus when restoring the previous editor. If the target does not become active, the save fails safely rather than saving another file. Explicitly opening a pending diff still focuses it. Browser diff review remains read-only.

Accepted writes include durability evidence. If format-on-save changes approved content, re-read when the result requests it. When saved formatting conflicts with the repository formatter or a save participant restores the baseline, inspect the saved file and save-participant configuration, then compose a new reviewed edit with `save_without_formatting: true` if exact preservation is intended. Do not repeat the same ordinary save or automatically change the user's formatter configuration. Protected targets, outside-workspace paths, and other policy boundaries remain reviewable. Foreground Review mode exposes `write_file` only for absolute paths inside the host temporary directory, such as Markdown bodies passed to review or approval commands; workspace files remain read-only. Normal write approval still applies. Background agents using the `review` tool profile remain fully read-only.

The standalone CLI exposes a narrower terminal-native contract: project-relative reads, bounded regex search, hash-bearing `get_context`, and single-file `write_file`/canonical SEARCH-DIVIDER-REPLACE `apply_diff`. Existing files require the saved baseline hash, new files require an absent-file precondition, and the terminal shows the complete resulting diff before approval. A session grant continues only the same tool and path along its verified content-hash chain; external edits, changed scope or policy, and switching between patch and replacement require a fresh review. CLI writes preserve exact content and return a verified final hash; they do not run VS Code format-on-save. After explicit managed TypeScript/JavaScript installation and separate typed enablement for the canonical project, the CLI also exposes read-only `get_diagnostics`, `get_symbols`, `go_to_definition`, `get_references`, and `get_hover`. These use project-relative paths, return explicit freshness/readiness metadata, and recheck file scopes before returning locations.

VS Code write/edit results report diagnostic samples only for the edited file, with bounded samples and pre-existing-error/line-shift filtering. They do not label errors from other files as caused by that edit. Diagnostic updates are observed over a bounded window, but the VS Code API supplies no source version for each diagnostic: an event or quiet interval is not compiler proof that an error belongs to the saved text or was caused by the edit. Non-empty samples are qualified accordingly, especially when no post-change event arrives, collection times out during updates, or the editor changes. A clean edit with no diagnostic event does not produce a pending warning. Disk durability is verified independently of diagnostic readiness.

Newly opened files get a bounded wait for pre-edit diagnostics before applying the proposal. An open document alone is not a clean diagnostics baseline. If no baseline becomes available, errors outside the edited lines are omitted and reported samples are explicitly unconfirmed as introduced by the edit. If the buffer changes during that wait, the proposal is not applied and the buffer is preserved. `read_file` diagnostic counts are cached language-service observations with unverified source freshness; matching open-editor dirty state flags that unsaved text may differ from the returned disk content. Neither reading correct disk text nor observing an editor version validates diagnostic source freshness. Use workspace diagnostics tools or the project's compiler/tests separately when checking wider effects.

Exact write-tool parameters and marker grammar: [write tools](complete-reference.md#write_file). Standalone CLI details: [Standalone CLI](standalone-cli.md).

When a VS Code edit save fails, `save_failure.save_outcome` distinguishes `returned_false` from `exception`. A supplied exception message is capped at 500 characters, with recognised credentials redacted, and returned as `vscode_error_message` with `vscode_error_detail: "available"`; missing messages remain `"unavailable"`. This is narrow redaction, not a guarantee that arbitrary formatter output is secret-free. The dirty buffer remains available for inspection and reviewed recovery.

## Generate, present, and save images

- `generate_image` is available in Code and Architect modes and defaults to GPT-Image-2.5 Flare for fast visual exploration. Use Sunburst when editing precision or final polish matters. OpenAI API-key sessions can select validated dimensions, quality through `max`, input fidelity, background transparency, PNG/JPEG/WebP output and compression, or explicitly edit a selected image with an optional PNG mask. ChatGPT/Codex OAuth keeps legacy generation and reference-led refinement; advanced controls are rejected before spending quota until that backend is verified.
- `present_images` shows images already retained in the session without generating a new image or consuming quota.
- `save_session_image` (VS Code, Code and Architect modes) writes an image already in the session, such as a pasted attachment, a screenshot, or a generated image, to a workspace file by its `image_N` ID. Bytes are written as stored, the file extension must match the image type, and existing files are replaced only with `overwrite: true`. It follows the same write approvals as file edits.
- Session image IDs stay the same after context condensing; the condense summary lists older images by ID without putting the images back into context. Details: [session image IDs](complete-reference.md#session-image-ids).

VS Code can save generated PNG, JPEG, and WebP files and use workspace-local edit/reference images. Browser Ask Agent remains display-only and uses retained session image IDs. Advanced calls require approval each time; legacy generation can still use **Generate for Session**. Partial streaming frames are never reported or saved as completed assets. Exact parameters: [image tools](complete-reference.md#generate_image).

## Run and inspect commands

Native commands check that the shell's current directory and the requested working directory refer to the same filesystem object, rather than trusting matching path strings. If a directory was deleted and recreated, the shell re-enters it using the logical path. If recovery fails, the command returns a nonzero exit without running the payload. When the directory still matches, no redundant `cd` changes `OLDPWD`, zsh directory hooks, or the directory stack. Unnamed commands still isolate shell mutations; named/targeted terminals still retain intentional shell state.

With Approve for Me active, normal index-only `git restore --staged` / `-S` is routine Git workflow and needs no Guardian model call, including on the native escalation required for Git metadata writes. Working-tree flags (`--worktree`, `-W`, or combined `-SW`), source overrides, and unsupported options remain reviewed. Guardian can approve restoring named workspace files only when task history and inspected changes establish that every discarded edit is disposable work from the current task. Broad restores, unrelated or mixed edits, and uncertain ownership still need direct user authorisation. A reason saying "cleanup" is not proof. Explicit rules, protected-file checks, and manual approval behaviour are unchanged.

Named or explicitly targeted **Native Agent** terminals retain intentional shell changes. Sandbox commands always use fresh shells, including when a terminal is named or targeted: an `export PATH=...` in one sandbox call does not change the next call. Supply non-reserved variables through `env` on every call (literal values, not shell expansion), or put dependent steps together in one reviewed command. Sandbox `PATH` is host-managed and reserved: do not pass `env.PATH`. To change executable lookup, include `export PATH="/desired/bin:$PATH" && command` in each reviewed sandbox call. Other host-managed entries, including HOME, temporary directories, proxy settings, and loader settings, remain reserved. Terminal identity and retained output are separate from shell-state persistence.

Prelaunch `sandbox_preparation_failed` results include a bounded `preparation_failure`: `reserved_path_override`, `reserved_environment_override`, `unsupported_shell_profile`, or `preparation_failed`. Known input/configuration errors are not attestation failures. Unknown preparation exceptions remain blocked with bounded host/request inspection guidance; raw exception text and environment values are not returned or logged by this classification. Existing typed security, integrity, drift, and grant errors keep their own recovery paths. None of these preparation failures authorises native fallback or automatic replay.

Prelaunch `sandbox_unavailable` results include a bounded `sandbox_diagnostic.category` when available, not raw probe output or exception text. Their non-automatic repair guidance distinguishes missing host Node runtime from failed security checks. `compile_failed` grant failures require checking request/policy mismatches before runtime assets, not repeated commands, assumed reinstallation or native bypass. Only the bounded reason is logged, not the raw compiler exception. Native shell startup timeouts require inspecting and repairing the selected shell profile's startup; reloading alone cannot fix a startup prompt or hang. See [terminal recovery](troubleshooting.md#a-terminal-tool-call-hangs-or-times-out).

- `execute_command` runs a command in a managed terminal. Under Approve for Me, default commands with complete direct Allow or Prompt rule coverage run natively; unmatched or partially covered commands stay sandboxed. Explicit sandbox-only requests and read-only execution stay sandboxed. An Allow rule skips the command card, a Prompt rule still asks, and Forbidden rules block execution. Command approval checks are ordered within each chat session, not across tabs: a pending approval in another tab does not block this session's checks or approval card. All authorization and shared workspace scheduling constraints remain in force. For an eligible default Approve for Me command, a confirmed sandbox runtime failure before command start offers one direct native approval, not a retry loop. The user must approve the exact command; rejection cannot be prompted again for that action in the same turn. Trust, security, invalid grants, uncertain launch state, and commands needing sandbox-only capabilities do not receive this fallback.
- `get_terminal_output` reads retained output or controls an observed command. Pass the `command_id` returned by native/sandbox `execute_command` together with `terminal_id` to read the same command after terminal reuse. Omitting it selects the latest command. An unavailable or expired command ID returns an error rather than another command's output; `kill: true` cannot interrupt a newer command when an older ID is selected.
- `close_terminals` closes managed terminals when appropriate.

The standalone CLI has a separate non-PTY command contract. Its `execute_command` uses an exact reviewed `/bin/zsh -c` launch with closed stdin, no persistent shell state, a project-contained working directory, and no sandbox claim. Environment values are omitted from approval and prepared-launch persistence; approvals retain variable names plus a host-keyed digest and revalidate the resolved environment before launch. Values of credential-like environment variables are redacted if a command prints them. `get_command_output`, `list_commands`, and `stop_command` operate on stable session-owned command IDs. Foreground commands hold the project mutation window until exit. Background development processes require typing `allow background` for each exact launch and remain observable through `/processes`, `/output ID`, and `/stop ID`. Retained interleaved output is bounded and reports dropped offsets; restart marks prior running records interrupted without reconnecting or replaying them.

Command history and output retention are bounded, not permanent storage. Earlier command IDs remain readable while their records are retained in an open terminal; closing or reclaiming a terminal retains only its latest command. Read final output before closing and use a returned `output_file` when available. Cleaned command text retains leading whitespace, blank lines and final newlines, with PTY CRLF line endings normalised to LF; saved output is cleaned text, not byte-for-byte raw stdout.

AgentLink redacts recognised Kubernetes Secret `data`/`stringData` in YAML or JSON terminal results and spills, and removes the object dump from recognised failed Secret Go-template output. It also redacts nonempty values on environment-style `NAME=value` lines whose names are `TOKEN`, `SECRET`, `API_KEY`, `PASSWORD`, or end in those underscore-delimited suffixes (case-insensitive, with an optional `export` prefix, starting at column one). Empty values remain visible for auth debugging. This happens before output filtering, in saved output files, in later `get_terminal_output` reads and when a command is force-completed. Force-completed partial output is bounded and does not claim a final output file. This is narrow accidental-disclosure protection, not a guarantee that arbitrary command output is secret-safe: unlabelled values, diff-prefixed or indented assignments, arbitrary formats and multiline environment values are not generically redacted, and the local terminal's raw output remains visible. Native/sandbox signal deaths include `signal` and a nonzero `exit_code` (128 + signal when the PTY supplied zero or no exit code), so an aborted process cannot look successful. Carriage returns move the output cursor without erasing text that has not been overwritten.

Command route, network access, shell persistence, and approval behavior depend on policy. Native Agent commands are dispatched through verified private command artifacts so complex approved shell text is not retyped through the interactive line editor. Readiness requires a nonce-bound confirmation emitted from the consumed artifact, not merely the outer shell-wrapper start. If dispatch ends without that confirmation, execution state stays unknown (`process_launched` is omitted), the result identifies a launch-stage failure with `retry_safe: false`, and captured launch diagnostics remain available through the normal output store. Inspect those diagnostics and any side effects before a new execution; no automatic replay is safe. Disposing a running process does not remove its input artifact before shell completion or terminal closure; unstarted proposals still clean up immediately. Bare SSH sessions remain blocked, while a command supplied after the SSH host is treated as one-shot/non-interactive. Safe `git init` chains targeting the workspace root receive protected-metadata native-retry guidance before launch. Use the structured recovery guidance returned by a failed command instead of guessing at retries. Recognized recovery includes bounded Turbopack listener cause chains, tsx Unix-socket denials, mise-wrapped container access and trusted-config writes, npm cache writes on managed-network routes, and Speakeasy/macOS TLS trust failures. Guidance never grants Unix IPC or container sockets, disables TLS checks, or automatically replays a compound command; isolate the failed step when earlier steps may already have succeeded.

Protected Git metadata preflight also recognises narrow Git-only `&&` and `;` workflows mixing writes (`add`, `commit`, local `user.name`/`user.email` setters) with inspections (`status`, supported `diff`/`ls-files`/`log`/`show`, author/committer `var`, and `remote -v`). It also recognises literal `printf` input piped to `git add --patch`/`-p` with file operands, including `git -c color.ui=false`. The same inspection allowlist supports quoted `test -z "$(git ls-files …)"` and `test -z "$(git diff …)"` guards before a writer. A constrained `git ls-files -z [-- paths] | xargs -0 git add --` pipeline is recognised too. Arbitrary or nested substitutions, script-running `xargs`, other configuration overrides, other dynamic input/output pipelines, and repository redirection remain outside that narrow preflight. A match only offers reviewed native execution before launch, never automatic permission or replay. Post-launch index and `ORIG_HEAD` lock denials, including linked-worktree metadata, receive Git recovery before generic HOME suggestions. When Git prints an internal `git apply` failure despite a zero shell exit code, the original exit code is preserved alongside `failure_evidence` and non-automatic recovery guidance. The same applies when a later command masks a recognised Git permission-denial diagnostic tied to protected metadata: `failure_evidence.code` is `protected_git_write_denied`, and recovery remains `protected_git_metadata`. Detection uses retained output before display filtering and does not claim which other steps succeeded. Inspect repository state before any reviewed retry because earlier hunks or workflow steps may already have changed it. GitHub TLS recovery recognises a `gh` step in a mixed workflow or review loop when the failure output identifies a GitHub request; it requires isolating the failed step and keeps certificate checks intact.

Sandbox helper failures return `sandbox_helper_failed`, a bounded failure category, `terminal_id`, `command_id`, and known launch evidence. Before readiness, launch state stays `unknown`; after readiness it stays `true`, but neither establishes the command's outcome. Retained output is included as a bounded preview with retention metadata. Use both IDs with `get_terminal_output` before deciding what to do next; no automatic replay is offered. Missing protected files remain write-denied, and later presence or content changes still invalidate their integrity snapshot. Command audit events record human approval requests before waiting and responses separately, excluding coordinator-only decisions and cancelled preflight.

`sandbox_protected_root_drift` identifies a protected snapshot change before launch, with a bounded relative path and change category. Inspect the change and request a newly prepared execution; repeated drift needs the concurrent host mutation resolved, not native bypass. A symbolic-link lock under shared `.git/worktrees/<name>/` metadata may belong to a live process: preserve it, inspect ownership, and use the separately reviewed native option when offered rather than deleting the lock. Hard links and other unexpected nodes retain their inspection/repair guidance.

For host-HOME write failures, commands or failure output identifying credential-backed configuration, or commands resolving through mise/asdf shims on a known sandbox PATH, do not receive disposable-HOME suggestions. An unrelated shim directory on PATH alone is not enough evidence. The `temporary_home_unsuitable` field explains the limitation, and the failed step can receive a separate native review that preserves host configuration. AgentLink does not trust toolchain configuration automatically. Finalized Docker socket permission denials receive the same non-automatic native guidance in `execute_command` and `get_terminal_output`, including deferred and recently closed commands with matching execution context. Running, incomplete, read-only, deliberately killed, prompt-terminated, or inline-file-dependent commands do not receive replay suggestions.

Recognised GitHub TLS or Git SSH failures in a compound command return managed-network recovery guidance even when its final segment exits `0`. SSH detection includes authentication-method negotiation failures and `Connection closed by UNKNOWN port`, including commands using a remote alias such as `origin`. The final exit code is preserved; it does not prove each earlier step succeeded. The guidance explicitly leaves individual segment outcomes uncertain, asks you to identify and isolate the candidate network step, and never permits replaying successful prefixes or disabling TLS verification.

Recognised Go dependency-download TLS failures (including `proxy.golang.org` certificate errors during `go test`) return `managed_network_tls_trust` guidance on the sandbox route. The underlying trust cause remains undetermined. Inspect partial changes and test output before choosing an exact separately reviewed retry: snapshot-updating tests may already have written files. Go recovery never offers blind same-command replay or disables certificate verification.

A managed `curl` exit 28 with reported HTTP status `000`, zero connection time and zero TLS-handshake time returns `managed_network_connect_timeout` and bounded evidence. This distinguishes an unestablished connection from a response delay without claiming the proxy is at fault. Inspect managed connectivity or request a separately approved native connectivity diagnostic; do not replay mutating requests blindly or disable TLS checks.

Read-only command profiles recognise bounded Git branch queries, including `git branch --all --contains HEAD`, optional reference filters, sort/format values, and explicit `--list` patterns. Branch creation, deletion, renaming, copying, upstream changes and unknown options remain rejected; query recognition does not grant network or write access.

Output-filter checks distinguish balanced `$()` command substitutions used to compute arguments or select inputs from visible terminal pipelines. For example, `files=$(list | head -3)` is not an output-filter violation, while `command | head -3` still requires `output_head`. Nested or quoted substitutions preserve this distinction; unresolved syntax remains conservative. File-write checks and command approval still apply.

Exact command-tool parameters: [terminal tools](complete-reference.md#execute_command).

## Work with people and the session

- `ask_user` asks structured questions. Host-authenticated human answers in VS Code and mirrored browser workspace chat can inform Guardian review of the matching session. The host binds the literal question, options, answer and note to its request and tool call; agent-authored question text is context, not independent human instructions. Coordinator replies, relays to another session and arbitrary tool output cannot create human authority. Rules, risk review and approvals remain in force.
- When a human answer or message arrives while Guardian is reviewing an `execute_command` call, the command is reviewed again; if the approval is still stale when the terminal is about to dispatch, nothing is sent and the result has `status: "authorization_stale"`, `command_sent: false` and `retry_safe: true`. Human approvals and `rejected_by_user` results that follow an automatic review include a `prior_review` object (review ID, status, outcome, model) so the agent can see what Guardian decided first.
- `todo_write` maintains visible work state. Every item, including nested children, needs a non-blank `id`, `content`, and `activeForm` plus a `status`; the schema describes these inline for up to three nesting levels so provider conversions keep them visible. Items missing a required field are ignored, and the model-visible correction names the missing fields. The list changes only when the agent calls the tool, so multi-step work should update it at each real task transition.
- `set_task_status` ends a turn with a truthful result. Clicking its Continue or custom next-step button adds the full prompt to the composer for review and editing, rather than sending it. Existing draft text and attachments are preserved. This applies in VS Code and browser chat, including Ask Agent; the separate Auto Continue setting still sends automatically when enabled.
- `switch_mode` changes the workflow mode.
- `search_session_history` and `read_session_excerpt` retrieve prior context when allowed.

## Delegate work

For native writable debugging, use `mode: "code"` or `taskClass: "debug"` with non-empty `ownedPaths`. The latter defaults to Code only from a Code-mode parent, when no explicit mode or review-only permission profile prevents it. Unscoped Debug remains investigative; foreground modes and ACP defaults are unchanged. Other mode/profile/skill/ownership restrictions still apply.

- `spawn_background_agent` starts a bounded background task. `modelTier` accepts `cheap`, `balanced`, `deep_reasoning`, or `foreground`; research defaults to the foreground model's tier, and other ordinary native work defaults below the foreground model when a configured tier group can satisfy it.
- `get_background_status`, `get_background_result`, `steer_background_agent`, and `kill_background_agent` supervise it. `get_background_result` keeps its single-session form and also accepts `sessionIds` with `return_when: "any" | "all"` for one cleanup-safe bounded wait across several agents.
- Fleet workflows can run structured review, browser verification, best-of-N work, or scheduled goals.

Orchestrate mode is the coordination-first workflow for delegating substantial research, codebase reading, implementation, validation, and review while keeping the frontier foreground model's context small. It chooses the lowest sufficient model tier, assigns non-overlapping writable scopes, monitors without tight polling, and integrates compact results rather than repeating each agent's investigation.

Use clear ownership and a focused review scope for writable or review work. Structured `ownedPaths`/`forbiddenPaths` are included verbatim in the child's task handoff when supplied. Native agents are told these are enforced path restrictions; ACP agents are told they are advisory. Forbidden paths take precedence, and steering or coordinator replies cannot expand the configured scope. Delegate a new scope or let the coordinator handle extra files instead. Native text and structured reviews receive bounded finalization recovery after an output limit or missing result. Empty text and unfinalized native review output are incomplete, not successful; partial output remains available. Explicit unsuccessful provider/ACP stops cannot turn partial output into a completed review. See [background agents](capabilities.md#background-agents-and-orchestration) and the [full background tool reference](complete-reference.md#spawn_background_agent).

`respond_to_background_question` returns `ownershipChanged: false`: an accepted answer resolves the question but cannot expand native write ownership. The coordinator must handle additional paths or spawn a replacement. The same reminder is included with coordinator question interjections.

## Connect external capabilities

- `find_mcp_tools` and `call_mcp_tool` discover and invoke configured MCP capabilities. In the CLI, untargeted discovery lists servers needing sign-in without connecting them; specifying a server connects only that server, and `call_mcp_tool` can invoke its tools in the same turn under the normal approval policy.
- Resources and prompts use `list_mcp_resources`, `read_mcp_resource`, `list_mcp_prompts`, and `get_mcp_prompt`.
- Native `web_search` and `web_fetch` may be available according to the configured web-access backend.

Native `review` and `readonly-research` profiles expose these public-web tools only when supported by the selected provider and enabled by current web policy. Active skill restrictions still apply. This does not authorise shell network access, credential-backed GitHub reads, or arbitrary `gh`/`curl` commands. When no supported web transport is available, fetch the material in the foreground and pass a local artifact to the child.

A Codex OAuth `web_fetch` can follow the provider's line-addressed continuation. The VS Code host keeps the inline result bounded and returns an AgentLink temp `output_file` for additional retained content; read it with `read_file` rather than repeating the fetch. If the provider still has more than AgentLink retained, continue from `next_start_line` with `start_line`. Browser Ask Agent does not expose host temp-file paths. An explicit `start_line` selects a page-open request even when `find` is supplied. Find-only reads can continue through navigation-only pages within existing limits, then preview the matching numbered source content while retaining the original pages. If the provider ignores the initial requested line or cannot reach the requested match before stalling or exhausting those limits, page access fails with `provider_page_focus_unavailable` so the existing hosted fallback can recover; navigation is not returned as a successful focused read. Continuation is based on returned line numbers, not the requested offset. Overlapping continuation pages retain only new line blocks. Unfocused reads that stall on a continuation retain earlier content with truncation and `output_warning`, and omit `next_start_line` rather than inviting a repeat loop.

A Codex page-access response consisting of the provider's `Internal Error ()` marker (with optional provider headers) is a failed read, not successful page content. Existing hosted fallback may recover an initial failure; otherwise the error names `provider_page_internal_error` and advises retrying the read or using another approved web transport. If only a continuation page fails, earlier content is retained with truncation/pagination-warning metadata, without appending the error text or claiming completion. An article that merely discusses the error is not rejected.

Codex hosted web requests use the normal Responses body and headers, including for OAuth models whose ordinary agent turns use Responses Lite. A Lite preference does not disable hosted fallback. Standalone page-access failures can therefore fall back to the selected model's hosted web search, which can also open pages, without changing models. The VS Code agent and browser Ask Agent use the same routing rule; ordinary turns without hosted tools retain their existing request format. Web policy, domain filters, approvals, and provider availability still apply.

MCP configuration and trust behavior: [MCP](mcp.md). Exact native web contracts: [web access](complete-reference.md#web-access).

## Report bugs and self-improvement opportunities in development builds

`send_feedback` helps AgentLink improve itself by collecting concrete bugs, workflow improvements, and feature requests grounded in actual use. Successful tasks can reveal unnecessary steps or missing capabilities too. Use the affected native tool name, or `tool_name: "agentlink"` for a cross-tool or general AgentLink workflow. Do not submit routine praise, generic wishlists, or third-party MCP-server defects; suggestions do not authorize self-modification or weaker safeguards.

New reports require a non-empty `observed_impact` describing an observed task consequence or unmet need. Preserve bug inputs, results, reproduction details, recovery, and recurrence; a bug report never needs a diagnosis or solution. Optional `category` is `bug`, `improvement`, or `feature_request`. Optional `suspected_cause` separates an unverified diagnosis from the evidence, and `suggested_change` captures a proposed fix, workflow improvement, or new capability. `workaround`, `observed_recurrence`, and `improvement_signal` capture recovery/outcome, occurrences actually observed, and a proposed observable success check. Report evidence, not importance scores, guessed prevalence, or invented savings. Reporting has no quota and must not derail the user's task.

`get_feedback` returns these fields when recorded. Older records remain readable without inferred categories or causes, with unchanged IDs and triage/deletion metadata. Reports stay bounded to 4,000 UTF-8 bytes; hypothesis and proposal text is shortened or omitted before existing bug evidence is shortened.

Validate bug evidence independently of the proposed fix. Review improvement/feature candidates against observed need, alternatives, product fit, and safety constraints without requiring a failing test. Bring worthwhile proposals to the user for approval and thoughts before accepting them with `triage_feedback`; backlog approval is not implementation permission. Deferred proposals remain active and untriaged, and useful P2/P3 improvements are not discarded merely for being lower priority. This is triage workflow guidance, not a new tool-enforced approval gate. The development sidebar shows supplied categories and separate expandable evidence, hypotheses, proposals, and success checks, all searchable. Exact contracts: [development feedback tools](complete-reference.md#development-feedback-tools).
