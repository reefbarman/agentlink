# Configuring MCP Servers in AgentLink

This is the owning guide for configuring and using MCP servers. See [Tools](tools.md) for agent-facing MCP tool families and the [complete reference](complete-reference.md#connect-the-built-in-agent-to-mcp-servers) for compatibility detail.

## UI entry points

- `/mcp` — open the shared MCP Manager (connection status, tools/resources/prompts counts)
- `/mcp-config` — configuration-oriented view (guided setup, JSON import, sources)
- `/mcp-refresh` — explicitly reconnect configured servers (ordinary catalog changes load automatically)
- `/mcp-watches`: reopen this chat's resource-watch controls in VS Code or its browser remote view

The MCP Manager has four views: **Overview** (config + status + enabled/disabled state), **Sources** (each layered file in precedence order, with read health and editability), **Guided setup** (stdio, HTTP, legacy SSE), and **Import JSON** (paste one or many servers; conflicts require explicit Skip/Replace/Rename). A multi-project workspace uses one Manager with a project selector. The Manager in both sidebar and editor chat panes updates after MCP config file changes. **Connect** starts an enabled server shown as "Configured · not connected" and may open sign-in. **Refresh** retries connections for the selected project and can initiate sign-in for configured servers without a runtime entry; **Reconnect** retries a server already in the runtime without forcing sign-in; **Reauthenticate** starts a fresh OAuth flow. Enable/disable changes remain configuration mutations. Actions return updated status to the pane where they were requested.

Failed server rows can be expanded even when no tools loaded. The expanded details show the complete, selectable error with wrapped text and preserved line breaks; hovering the shortened summary also shows the full error. This uses the same Manager in VS Code and browser workspace chat.

If a tool call detects that its connection's configuration is no longer current, AgentLink rejects the call and marks that connection as an error. Subsequent discovery no longer advertises its tools, resources or prompts as usable. Inspect the configuration diagnostic and use **Reconnect** with the current configuration when appropriate. This does not reconnect automatically or bypass tool approvals or plugin authorisation.

Server rows stay compact and single-line when space permits. Narrow panels hide secondary counts and badges before wrapping the action buttons; the status icon and server-name tooltips retain the full status, counts, transport, and source labels. The status icon also exposes these details to screen readers. The layout follows the Manager's own width, including a narrow chat pane inside a wider browser window.

### Desktop MCP window

In standalone Desktop, **More → MCP** and the **MCP Servers…** app-menu item open a separate, resizable manager window. `/mcp`, `/mcp-config`, and `/mcp-refresh` open that same window rather than a panel beside the composer. Reopening focuses the existing window; closing it does not disconnect servers.

The window uses the same server-management controls as VS Code: add/edit, import JSON, remove, enable/disable, connection recovery, environment/header configuration, and native raw-config opening. It shows live connection state and tool/resource/prompt counts. **Refresh** retries quietly. **Connect** and **Reconnect** recover one configured server without clearing its credentials; **Reauthenticate** starts a fresh remote OAuth sign-in. When first use or an explicit Connect/Reconnect/Reauthenticate action needs sign-in, Desktop opens the system browser directly without an extra confirmation card. Complete or decline sign-in on the provider's page. Closing the browser tab does not immediately cancel the pending connection; use **Cancel** in the manager to stop it, or let it time out. Closing the window cancels its manual sign-in, not an unrelated agent turn. Completed and cancelled operation banners can be dismissed and clear automatically after five seconds; failures remain visible until dismissed. Manual connection actions are unavailable during an active turn; an outstanding manual action must finish or be cancelled before an agent turn can start.

Desktop MCP tool approval offers **This Tool** or **Whole MCP**, with **Session** or **Global** rule scopes. Project controls are hidden because Desktop is projectless. **Session** applies only to the current conversation. **Global** writes the shared `~/.agentlink/mcp.json`: a tool rule adds to `allowedTools`, while a whole-server rule sets `toolPolicy: "allow"`. Desktop and VS Code both load these rules on later connections/turns, including after restart; more-specific project settings can override them. If an existing Ask Agent policy would hide the saved approval, Desktop updates that policy too. Existing connection fields and credentials are preserved. Shared Global approval requires a server connection defined in the global sources; for a server defined only in the Ask Agent profile, use Session or configure a shared global definition first. A failed save leaves the approval open and does not allow the tool. Shared Global rules must be saved from native Desktop or a loopback client, not a LAN browser session.

Desktop uses the projectless Ask Agent profile. Structured server edits are saved to `~/.agentlink/ask-agent/mcp.json`; inherited global definitions remain unchanged except when explicitly saving a shared Global approval rule. **Inherited** is a source label, not an error, and **HTTP** is a transport label. Editing or disabling an inherited server creates an override. Fields omitted from that override, including existing headers/environment values, remain inherited. Removing an override reveals the inherited definition again. Configuration stays saved if reconnection fails. Raw config opening uses the Desktop's native bridge, not a browser-remote endpoint.

Native Desktop MCP connections follow VS Code's HTTP(S) networking, including localhost, private LAN, Tailscale, and private identity providers. Desktop does not add a public-network-only OAuth filter. TLS verification, first-use sign-in gating, callback state validation, cancellation, and isolated credential storage still apply. MCP tool-call approvals are unchanged. Browser-remote secret/local-process restrictions remain separate.

Desktop's native HTTP/SSE connections can refresh tokens silently while idle. Browser-owning `mcp-remote` proxies are started or relaunched in the background only when their cache has a usable, unexpired access token; otherwise they wait for targeted use or an explicit connection action. This avoids treating a refresh token alone as proof that a proxy will stay noninteractive. A proxy with a revoked but unexpired token, or another local process that opens its own browser, is outside AgentLink's native OAuth browser gate.

## Config files and precedence

For each project, server definitions merge from these files in ascending priority (later overrides earlier for the same server name):

1. `~/.agents/mcp.json`
2. `~/.claude/mcp.json`
3. `~/.agentlink/mcp.json`
4. `<workspace>/.agents/mcp.json`
5. `<workspace>/.claude/mcp.json`
6. `<workspace>/.agentlink/mcp.json`

AgentLink writes structured changes only to `.agentlink/mcp.json` sources (project or global). To change an inherited `.agents`/`.claude` server, create an AgentLink-owned override instead of editing those files. Projectless Ask Agent loads global compatibility sources followed by `~/.agentlink/ask-agent/mcp.json`; the standalone Desktop preview uses this same configuration without requiring VS Code. On macOS and Linux, Desktop starts its helper with the login shell's `PATH` (zsh on macOS and bash on Linux when `SHELL` is unset) so global stdio servers using commands such as `npx` can resolve even when the app is launched from Finder or a desktop launcher. Desktop on Linux cannot sign in to OAuth MCP servers yet. If shell startup fails, it keeps the inherited `PATH`; an unavailable executable is omitted from the Desktop turn rather than failing the question. Restart Desktop after changing your shell's executable paths.

The main agent receives the union of every available workspace project's effective servers. Identical definitions are connected once. Different same-name definitions are kept under stable project-qualified runtime names, so one project's MCP config cannot silently hide another's.

## File format

Standard `mcpServers` object:

```json
{
  "mcpServers": {
    "example": {
      "command": "example-mcp-server",
      "args": ["--stdio"],
      "timeout": 300000,
      "toolPolicy": "ask",
      "supportsParallelToolCalls": false,
      "disabled": false
    }
  }
}
```

- HTTP servers use `url` (`serverUrl` is normalized to `url`; `streamable-http` normalizes to `http`).
- JSONC, UTF-8 BOM, and a single complete ```json fence are accepted on import; unknown client-specific fields are reported as **Not imported**, not silently written.
- Prefer `${VAR}` references for secrets in env values and headers — AgentLink expands them at runtime. Values are masked in the UI but stored plaintext in the file. URL userinfo is rejected; don't put credentials in args or query strings.
- `disabled: true` persists across refresh/reload and removes the server's tools from the runtime.
- `timeout` is the per-tool-call inactivity timeout in milliseconds (default: `60000`). AgentLink respects any positive finite configured value; MCP progress notifications reset the inactivity window, and HTTP/SSE transport deadlines do not shorten it. There is no separate hidden total cap: an active server can extend the call by continuing to report progress, while caller cancellation still stops it.
- MCP tools run concurrently only when the tool advertises the read-only annotation, or when the server opts in via `supportsParallelToolCalls: true`.
- `cwd` sets a stdio server's working directory. A relative path resolves against the folder that holds the config's `.agentlink`, `.claude` or `.agents` directory: the project root for project configs, and your home folder for global and Ask Agent configs. `~` expands to your home folder. Without `cwd`, the server starts in the host process's working directory, which is usually not your project, so set `"cwd": "."` in a project config when `command` or `args` use project-relative paths such as `scripts/server.sh`. HTTP and SSE servers reject `cwd`. It has no MCP Manager control; saving the server from the Manager keeps it.
- `protocol` chooses the MCP protocol version: `"auto"` (default), `"legacy"` or `"2026-07-28"`. See **Protocol versions** below. It has no MCP Manager control; set it by editing `mcp.json`. Saving the server from the MCP Manager keeps it.

## Run MCP prompts from the composer

In an existing VS Code workspace chat, type `/` to find connected servers' prompts alongside other slash commands. The browser remote view uses the same composer and approval card. A prompt named `ask` from server `agent-comms` appears as `/agent-comms:ask` in the **MCP Prompts** group. Search by server or prompt name, for example `/age` finds `agent-comms` prompts. Existing commands take precedence if their names collide. Refreshing the slash picker reads the current prompt catalogue.

- Type arguments in the order shown by the hint (`<required> [optional]`). The final positional argument takes the rest of the line: `/agent-comms:ask tab-2 can you check the build?`.
- Use double quotes around an argument containing spaces, or `name=value` / `name="value with spaces"` to choose an argument explicitly and skip optional ones. Put named arguments before the final free-text argument; `name=value` inside that free text stays literal.
- If the server advertises completions, AgentLink calls standard MCP `completion/complete` for the argument being edited and shows a labelled popup for that argument, including its description and whether it is required. Suggestions refresh when you click or move the cursor back into a pasted command, not just when typing. Use Up/Down to navigate, Tab or Enter to select without submitting, or Escape to close the suggestions. Selecting a value keeps the rest of the command intact. Requests are debounced, time out after five seconds, and show at most 20 suggestions of up to 200 characters. Completion failure does not prevent typing a value yourself.
- Submitting fetches the prompt with `prompts/get` and shows its text in an **MCP Prompt** card in the Chat Activity Shelf. Nothing reaches the agent before you approve it. **Send Once** adds the server-written text to the chat with an MCP provenance block, not as words you typed. The transcript shows a compact, expandable **MCP prompt** card labelled with the server and prompt name, rather than showing the wrapper tags and model-facing provenance text. Expand it to read the server's template; any introduction or follow-up you wrote stays outside the card. Copy copies the readable text without the wrapper. Stored messages and the agent's context retain the original provenance block, including in restored chats; this is a display change, not a tool call or an approval grant. Tool calls it requests still pass through their normal approval/Guardian checks.
- The card can save a rule for **This Prompt** or **All Prompts**, scoped to **Session**, **Project**, or **Global**. Session rules last only for that conversation and do not survive reload or pass to background agents. Project/global rules persist as `allowedPrompts` or `promptPolicy: "allow"` in the corresponding `.agentlink/mcp.json`. Rules for prompts are separate from `allowedTools` / `toolPolicy`, and do not approve notifications, tools, resource updates or idle wake. Plugin servers offer session prompt rules only.
- Switching chats cancels the pending admission. A disconnected browser request or expired approval also cancels it, so an orphaned prompt card cannot later send into a different chat. Declining keeps your command in the composer. Prompts over 32,000 characters are refused rather than truncated.

This slice supports text and embedded text resources. Other content types appear as labelled placeholders in the approval card, and assistant-role template messages retain their role label inside the server-content block rather than being injected as actual assistant history. Prompt slash commands are not yet exposed in standalone Desktop/Ask Agent, the CLI or Assistant. Agent-facing `list_mcp_prompts` and `get_mcp_prompt` remain available as before. This feature does not subscribe to resources or wake idle sessions.

## Session-approved resource notifications and idle waking

In VS Code workspace chats and their browser remote view, an agent can request `watch_mcp_resource` for one exact server/resource URI when updates are needed for your task. No slash command is required: you can ask cooperating tabs to register and watch their inboxes. The server must advertise resource subscriptions. Registration, connecting a server, enabling Auto Continue, and approving its tools or prompts do not create a watch.

An **MCP resource watch** approval card identifies the session, server and URI. Choose:

| Choice                    | Behaviour                                                                                                                                                |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Notify only**           | Show update metadata in the Chat Activity Shelf. Do not fetch content or start an agent turn.                                                            |
| **Deliver automatically** | Repeatedly read that exact resource and queue its text for a running turn's next safe boundary, or the next turn you start. Do not wake an idle session. |
| **Deliver and wake**      | Also allow normal agent turns while idle, which can use model tokens while you are away.                                                                 |
| **Deny**                  | Do not subscribe, read, deliver or wake.                                                                                                                 |

Standing permission requires your explicit card choice, including with **Approve for Me** enabled. It applies only to this loaded session, server definition and exact URI. It is not inherited by background agents or another tab, does not grant permission for other resources or tools, and is cleared on session closure or reload. Reconnecting an unchanged server retains permission; changing its definition requires fresh approval. Notifications cannot create approval cards or grant themselves permission.

After an automatic-delivery grant, there is no card or model tool call for each resource read. Reads are non-interactive: a sign-in or server-input requirement pauses the watch instead of opening a browser or form. Only bounded text snapshots are delivered, not binary attachments or linked resources. Updates appear as clearly labelled, expandable tool-style MCP resource blocks, not user-authored messages or executed tool calls. The collapsed row shows the server and an expand chevron; opening it shows the exact resource URI, a trust notice and plain-text content. It never follows embedded links or renders remote images. When an idle tab wakes, activity becomes visible during preparation, before model text or reasoning arrives, without making the previous completed answer look active again. VS Code and the browser remote view share this rendering. Their content cannot authorise actions, approve requests or change your task. Ordinary tool, mode and Guardian checks still apply to any actions the agent takes.

The compact **Resource watches** panel shows each server, inbox/resource URI, permission level and pending-update state. Its close button hides only the panel, leaving watches and permissions unchanged. It stays hidden through routine updates and unchanged tab switches in the current chat view; type `/mcp-watches` to reopen it. Adding a new watch automatically reveals the panel and expands the Shelf enough to show it, including after dismissal, but only after its approval completes. Pending watch requests are not listed as watches; while an approval card is open, watch controls stay hidden so the card remains visible and keeps focus. Pending messages, pause/resume changes and duplicate snapshots do not reopen a dismissed panel. A persistent **MCP update available** indicator on the Chat Activity Shelf shows the number of watches with pending updates, even when the panel is hidden or the Shelf is collapsed. Clicking it opens the watches and reveals the controls, without reading content, starting a turn or acknowledging messages. Opening the panel does not clear pending state; the indicator disappears when no watches have pending updates. For Notify only, a successful **Send once** clears the notice once the snapshot is admitted to the agent's context, or immediately if the approved read returns empty text. Failed, denied or undelivered reads leave it pending, and a newer notification arriving during the read/delivery remains pending. This acknowledges the local update notice, not the server's messages: agent-comms still uses `read_messages` to mark mail read. While an approval or MCP input request is open, the indicator stays visible but cannot open watch controls or take focus away from that request. Notify only remains metadata-only: the agent does not receive the resource body or wake because of this indicator. This command changes only the UI, never starts a model turn or grants permission. The same controls and visibility behaviour are available in the browser remote view of a VS Code chat.

Use the Shelf's **Pause**, **Resume**, **Stop watching** and **Send once** controls. Stop watching cancels automatic reads and discards undelivered updates; it cannot recall content already admitted. Send once requests a separately approved one-time read/delivery without enabling a standing watch. Its control request completes once the approved snapshot is queued, not when the resulting agent turn finishes. Browser watch controls become usable again while that turn runs or asks a question; later turn failures appear in the normal session error UI. Explicit session Stop suspends automatic delivery and waking. A new user turn can resume an approved stop-paused watch, but does not undo a manual watch pause. Sessions awaiting a question or approval are not automatically started, and completed background agents are not resurrected.

Transport bounds apply even if a server floods notifications: four watches, coalescing and unchanged-snapshot suppression; 64 KiB per resource read and 128 KiB queued per session; at most six automatic reads per minute across the session and one read per watch per five seconds. Approved automatic delivery and idle waking have no separate batch-count or wake-count budget and do not require periodic user turns or Resume. Wake-started turns use normal agent execution and the session's existing Auto Continue setting, with no special model-round or tool-call cap. This applies to every watched MCP server, not just agent-to-agent messaging. Revoked or unsubmitted updates cannot continue an old task. Notifications can therefore cause sustained work and token use while permission remains active; use Pause, session Stop or Stop watching to intervene. A paused/error state is visible in the Shelf.

Transport uses standard `notifications/resources/updated`: per-session `subscriptions/listen` resource filters on MCP 2026-07-28, and shared/ref-counted `resources/subscribe` on the 2025-era protocol. Notifications carry update metadata, not trusted message bodies; authorised resource reads obtain the content. This is latest-snapshot delivery rather than an exactly-once mailbox protocol. For agent-comms, resource reads peek at unread mail without marking it read; the existing `read_messages` tool acknowledges it under normal tool policy.

Standalone Desktop/Ask Agent, CLI and Assistant do not expose watch/delivery tools yet. Their ordinary MCP resource reads are unchanged. The shared connection transport supports resource subscriptions, but hosts must supply session consent and delivery lifecycle support before advertising watches.

## Protocol versions

AgentLink speaks both MCP 2026-07-28 and the 2025-era protocol. With `protocol` unset or `"auto"`, it first asks the server which versions it supports (`server/discover`) and uses 2026-07-28 when offered, otherwise the 2025-era `initialize` handshake. For a `stdio` server this check starts a short-lived second copy of the server, and a server that does not answer within 10 seconds is treated as 2025-era. The answer is remembered per server for 7 days, and any change to the server's URL, command, arguments, working directory, environment or headers checks again, so later connections skip the check. On a remembered 2026-07-28 connection AgentLink still asks the live server for its current capabilities once (one request, no second copy of the server), so a server updated in place is noticed straight away; if its capabilities changed, AgentLink reconnects once to use them. VS Code keeps it across reloads and windows; Desktop and the CLI remember it until the process exits. If a remembered answer fails to connect, AgentLink forgets it and checks again on the next attempt. An HTTP server that rejects the check with a server error or an unreadable reply is treated as 2025-era, so the automatic retry uses the older handshake; a network failure is not. A `stdio` server run through `mcp-remote` is not checked and uses the 2025-era handshake, because a second copy would start a second sign-in or token refresh; set `protocol: "2026-07-28"` to force the newer version. While a server waits for browser sign-in, AgentLink checks again instead of reusing a remembered 2026-07-28 answer, so sign-in keeps its 10-minute window.

- `"legacy"` always uses the 2025-era handshake. Use it for a server that misbehaves when asked which versions it supports.
- `"2026-07-28"` requires 2026-07-28 and fails the connection if the server does not offer it.

On a 2026-07-28 connection:

- Change notifications (`list_changed`) arrive on a stream AgentLink opens to the server. If that stream drops while the server stays connected, AgentLink reopens it with backoff (1, 2, 4, 8, 16, then 30 seconds; it stops after six quick failures in a row) and refreshes the affected lists, because notifications sent during the gap were lost. A stream that stayed open for 60 seconds resets that budget.
- A server asks for input by answering a tool call, resource read or prompt request with a request for input instead of sending a separate request. AgentLink shows the same form or link prompt as before and retries the original call with your answer, for at most 10 rounds per call. A server's URL prompt does not tell AgentLink when the browser step finishes on this protocol version, so close the prompt yourself when you are done.

## Session context for servers that ask for it

AgentLink offers an MCP extension, `dev.agentlink/session-context`, in its client capabilities (`capabilities.extensions`) on both protocol versions. A server that also lists it in its own `capabilities.extensions` (or `capabilities.experimental`, for older server SDKs) receives the calling chat's identity on each VS Code tool call, user-run prompt fetch, prompt-argument completion and approved resource-watch request/read, in the request's `_meta` under the same key:

```json
{
  "_meta": {
    "dev.agentlink/session-context": {
      "sessionId": "1a2b3c4d-…",
      "label": "tab-2",
      "kind": "foreground"
    }
  }
}
```

- `label` is `tab-N` for chat tab N, or `tab-N/bg-<short id>` for a background agent started from it. Background agents also send `parentSessionId`.
- `sessionId` is AgentLink's stable session ID, so a later chat that reuses tab number 2 is a different identity.
- AgentLink sets these values, not the model. They are still client-declared: a server must not treat them as authentication.
- Servers that do not list the extension receive nothing. The context starts from a chat's first turn in a tab; before then, and in Desktop, the CLI and Ask Agent, calls carry no context. Ordinary agent-initiated resource reads and agent-fetched prompts do not carry it yet; approved resource watches and their automatic reads do.

## MCP from Agent Plugins

Canonical Agent Plugins 1.0.0 may declare `stdio`, Streamable HTTP, and legacy SSE servers. These definitions are immutable package content rather than ordinary `mcp.json` sources: connection details are shown in the Agent Plugin install/update review and cannot be edited in the MCP Manager. AgentLink-owned overlays can disable a plugin server or change its tool policy, allowlist, disclosure, and parallel-call setting without modifying the package.

Plugin servers are scoped to global or one canonical project identity. The requesting project receives its enabled global servers plus its own enabled project servers; another project's plugin server is excluded. A project plugin shadows a global plugin with the same manifest name. Projectless sessions receive no plugin MCP servers. Each server connects independently so one invalid, offline, or authentication-failing entry does not block its siblings.

For `stdio`, `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` are expanded only in arguments, environment values, and `cwd`; command tokens, URLs, and headers are never interpolated. `PLUGIN_ROOT` points at the reviewed immutable package generation. `PLUGIN_DATA` points at persistent AgentLink-owned data that survives updates and ordinary uninstall/reinstall. **The server process runs locally outside AgentLink's command sandbox**, so review its command, arguments, working directory, and environment before enabling the plugin. No dependency or setup hooks run automatically. MCP tool calls still use ordinary discovery and approval policy after connection.

For Streamable HTTP and SSE, configured headers are injected only for the reviewed MCP origin. They are not sent to OAuth endpoints, cross-origin redirects, or cross-origin SSE endpoint events; client- and OAuth-controlled headers take precedence. Plugin transports do not silently fall back to another transport type.

Plugin MCP entries appear read-only in the main MCP Manager and in the Agent Plugin manager. The browser remote may inspect bounded status and policy summaries but cannot mutate plugin state or configuration. Agent Plugin management itself is documented in `references/customization.md`.

## Behavior notes

- Repeated connect-then-crash cycles have a shared maximum of five automatic reconnects, with 1/2/4/8/16-second delays. A successful connection resets that budget only after staying connected for at least 60 seconds; a manual reconnect starts a fresh budget. In VS Code, retries re-read the effective configuration and stop if the server was removed, disabled or changed, so stale queued work cannot restart an old definition.

- Saving and connecting are separate: a valid config stays saved even when the server is offline or needs auth.
- When a server sends `notifications/tools/list_changed` (or the resource or prompt equivalent), AgentLink re-fetches that list in the background and keeps the previous list if the re-fetch fails.
- While an MCP tool runs, progress the server reports (`notifications/progress`) appears under its tool row in VS Code and the browser view: a bar with a percentage when the server gives a total, plus the server's message (up to 500 characters, shown as plain text). Without a total, only the message is shown, or the raw count when there is no message. Progress is display-only: the model never sees it, it disappears when the call finishes, and it also keeps the call's inactivity timeout from expiring. Compose child calls do not show progress.
- When a server asks for input during a call (a form, or a link to open in your browser), the request appears as a card in the Chat Activity Shelf above the composer, in VS Code and the browser view, instead of a pop-up. The card shows the server name, its message and the fields; fields the server did not title get a readable label from their name (`favouriteColour` shows as "Favourite colour"), and optional fields are marked. Link cards show the origin and full URL and warn about local or private network addresses; the link is never opened until you choose **Open page**. Each card has three actions: **Submit** (or **Open page**) answers, **Decline** tells the server you will not provide it, and **Cancel** dismisses the request without an answer. Servers can treat Decline and Cancel differently.
- After you answer, the tool row records what was asked and what you chose (Submitted, Opened, Declined or Cancelled); expand the row to see your answers as label and value pairs. This record is display-only and the model does not see it. It is only attached when exactly one call to that server is running, so it is never guessed for parallel calls.
- MCP tool results are passed to the model as the server returned them, with one narrow exception. When a result contains the OpenAI/ChatGPT device sign-in callback URL (`https://auth.openai.com/deviceauth/callback`), for example in a browser server's page list, the `code` and `state` values are replaced with `REDACTED` in text, structured content and metadata before the model sees them. The rest of the URL and every other URL are unchanged. This is not a general secret scanner, and tool arguments, navigation and sign-in itself are not affected. Using a dedicated browser profile for automation still keeps unrelated tabs out of results entirely.
- MCP OAuth token endpoints must use HTTPS. Plain HTTP is accepted only on `localhost`, `*.localhost`, `127.0.0.1` and `::1`, so an authorization server on a private LAN or Tailscale address needs TLS; there is no opt-out. AgentLink also passes the sign-in callback's `iss` to the MCP SDK and remembers which authorization server a sign-in started with, so a callback from a different authorization server is rejected before its code is exchanged (RFC 9207). These checks apply in VS Code, Desktop, the CLI and the Assistant.
- HTTP OAuth is coordinated across project hubs and open VS Code windows. Automatic connection recovery can open at most one authorization flow for a server at a time; other attempts pause with a **Reauthenticate** action instead of opening duplicate browser tabs. A short post-flow cooldown blocks repeated automatic prompts, while an explicit Reauthenticate may bypass the cooldown after any active flow finishes.
- AgentLink continues to use a configured `mcp-remote` command as the MCP transport. A proxy with cached credentials may start in the background so it can refresh silently. A cache-cold proxy waits until an agent first uses that specific server before starting interactive login. Servers that require browser sign-in during a silent connection also wait for first use. Unrelated messages and other MCP servers do not start that login; the agent can find waiting server names with `find_mcp_tools` and request a specific server to discover its tools. A waiting server shows a **Sign in** button in the MCP panel that starts its browser sign-in immediately; explicit Connect and Reauthenticate actions can also start sign-in. Browser sign-in may take up to 10 minutes (for example, to complete 2FA). If sign-in finishes after AgentLink stopped waiting, the server reconnects with the new credentials automatically. A stale OAuth client registration is cleared and retried once silently; only a failed retry is reported. If initial proxy startup fails, AgentLink pauses automatic startup retries instead of repeatedly relaunching the proxy and browser. The error preserves the underlying connection failure and bounded, redacted process stderr when available. Inspect that diagnostic and the server configuration before another manual **Reconnect**; use **Reauthenticate** only when the diagnostic indicates an authentication failure. A generic "Connection closed" does not itself prove an auth failure. Startup output above 32 KiB is omitted rather than returning partially captured credentials; displayed diagnostics are capped at 8,192 characters. A proxy that connected successfully and later drops still reconnects in the background.
- In VS Code-backed MCP connections, disabling or disconnecting a server cancels queued connection attempts and pending OAuth prompts/callbacks, including manual reauthentication. Cancelled work cannot later reopen sign-in or reconnect the server. An unanswered refresh-failure reauthentication prompt expires after 60 seconds; the browser callback waits up to 10 minutes. Use **Reauthenticate** to start a fresh attempt. Already-open browser tabs or VS Code notifications may remain visible, but late responses do not resume the cancelled flow.
- When a Streamable HTTP server stops recognising AgentLink's MCP session (usually because it restarted and answers HTTP 404 to the old session ID), AgentLink starts a fresh session without OAuth prompts and reloads the server's catalog. The call that hit the expired session is not retried automatically: it returns `mcp_session_expired` with `retrySafe: false`, and later calls use the new session. A 404 without an established session is still reported as an ordinary connection failure.
- MCP config reloads preserve which servers were already known, so touching an existing config does not reclassify every OAuth server as newly added or trigger interactive authorization. When another window refreshes shared credentials first, the waiting connection retries silently with the newer token generation.
- For local diagnostics, `npm run telemetry:mcp-auth` summarizes bounded MCP auth events from `~/.agentlink/mcp-auth-telemetry.jsonl`, including browser-open bursts, trigger paths, refresh fallbacks, and lease contention. It never records tokens, headers, authorization URLs, callback parameters, or raw SDK errors; server identities are locally salted in telemetry.
- Writes are revision-checked and atomic; concurrent external edits produce a `config_changed` result rather than an overwrite.
- In VS Code-backed sessions and standalone Desktop, configured servers that failed to connect remain visible to the agent instead of disappearing from discovery. `find_mcp_tools` returns connection status and errors alongside tool results; targeting a failed server returns its diagnostic as an error, not an unexplained empty tool list. Targeting a sign-in-pending server still starts only that server's first-use connection. Inspecting a paused failure does not automatically relaunch it or clear credentials.
- Large catalogs are progressively disclosed (`find_mcp_tools` / `call_mcp_tool`); the same approval model applies to MCP tools as to native ones. MCP runtime names containing characters that provider function APIs reject, or exceeding their portable length limit, are also routed through this bridge, so one incompatible server or tool name cannot invalidate the whole model request.
- In VS Code-backed sessions (including browser remote), **Approve for Me** reviews MCP calls not already covered by an MCP grant through Guardian. An allow covers only that exact server, tool, arguments, definition, live session and approval context, once. It never saves a rule. A Guardian denial immediately pauses the call for the normal MCP human approval card, with the Guardian explanation and call arguments visible. The call runs only if the human explicitly allows it; a human denial still rejects execution. Retained denials and repeated-denial interruptions continue to require a human decision rather than another automatic review. The VS Code modal fallback shows the explanation too. Human approval does not override skill, read-only, server-side path or other hard access restrictions. High/critical-risk allows, unavailable review or payloads too large to review completely retain the ordinary human approval path. Manual mode and standalone Desktop/CLI approval behaviour are unchanged.
- The optional Jev first pass uses the existing `agentlink.guardian.typeSafeShadow.enabled` and `agentlink.guardian.typeSafeShadow.firstPass.enabled` settings and stored TypeSafe API key. It sends complete tool definitions, arguments and review context only when bounded and non-sensitive. Authorization, task relevance, safety and bounded-impact probabilities must meet `firstPass.threshold`. Missing, redacted, oversized, uncertain or failed evidence falls back to full Guardian review. Jev never denies a call itself. First-pass MCP allows skip full review, unlike command first-pass approvals, which retain their background audit.
- Guardian cannot bypass skill allowlists, read-only/background restrictions or compose admission. Compose still requires pre-approved, read-only MCP tools. MCP connection and browser sign-in approvals are not tool-call approvals and remain unchanged.
- A timeout or cancellation leaves remote completion unknown. AgentLink does not automatically retry; check a server-provided status/read operation before repeating a potentially mutating call.
- Browser surfaces backed by VS Code: main-profile browser config is read-only; loopback Browser Ask Agent may configure local-process servers; LAN sessions may configure only secret-free HTTP/SSE servers. Remote browser edits cannot change an existing server's URL or transport while retaining stored/inherited environment or header credentials. Make those changes locally in VS Code or native Desktop. This restriction applies to browser-remote writes, not native Desktop MCP networking.
- Standalone Desktop connects enabled, configured servers quietly at helper startup and retains those connections across turns and conversations. Config changes are reconciled automatically without restarting unchanged connections. Servers needing browser sign-in wait until the agent targets one by name with `find_mcp_tools`, a tool call, resource read, or prompt request; unrelated turns do not open the sign-in browser. Standalone Desktop executes tools pre-authorized by `toolPolicy: "allow"` or `allowedTools`; tools using the default `ask` policy display an MCP approval card with allow-once, current-conversation tool/server rules, and shared Global tool/server rules. Conversation grants are runtime-only and disappear when the helper stops or the conversation is deleted; Global rules persist in the shared MCP configuration. Standalone Desktop also lists and reads configured MCP resources and prompt templates without VS Code. MCP form elicitation uses the same validated activity-shelf controls as the remote browser and cancels with the active turn.
- Desktop only starts a configured `mcp-remote` proxy unattended when its cache has a usable, unexpired access token. An expired token with a refresh token still waits for targeted use or manual connection. This gate also applies to background reconnects. A revoked token that appears unexpired, or an arbitrary local process that opens its own browser, cannot be universally controlled by AgentLink's native first-use OAuth gate.
- The CLI uses the shared per-session MCP runtime to expose `find_mcp_tools` and `call_mcp_tool` for servers awaiting first-use sign-in, plus `list_mcp_resources`, `read_mcp_resource`, `list_mcp_prompts`, and `get_mcp_prompt` alongside connected server tools. Discovering tools without a server name lists servers needing sign-in without connecting them; targeting a server connects only that server, and its tools can be called in the same turn. Resource and prompt reads require a current enabled server definition, but do not prompt for per-call approval. Server form elicitation opens an interactive terminal control, validates submitted fields, and cancels when the operation or turn ends. Multiple calls from the same turn to one server share an elicitation owner. Hub connection status and warnings appear in the CLI status line; `agentlink mcp status` still reports configuration, not live connections. Use `agentlink mcp reauthenticate <server-name> --project <path>` from an interactive terminal to replace the CLI's OAuth credentials for an enabled remote server. It requires typed confirmation and a separate browser-opening confirmation after the OAuth destination passes the public HTTPS check. Existing tokens remain available if the new sign-in is cancelled or fails; successful sign-in replaces them.
- On macOS, standalone Desktop opens the system browser directly when targeted first use or an explicit connection action requires OAuth, without an extra confirmation card. Native Desktop supports the same HTTP(S) MCP and OAuth network destinations as VS Code, including private networks and local development servers; normal SDK/native fetch redirect behaviour applies. The helper receives a state-bound callback on its loopback listener and stores dynamic client registration plus tokens in Keychain without exposing credentials to the Electron renderer or browser client. Silent refresh uses the same native networking as sign-in. Disabled, removed, or changed configurations cannot resume stale sign-in work or save late tokens. The desktop browser callback uses AgentLink's branded page and says **Authorization received / Finishing setup** until the app completes token exchange; it is not itself confirmation that the connection is ready. The helper retains shared MCP connections across conversations; finishing, cancelling, or deleting a conversation releases its action authority without closing other ready connections. Changed, removed, or disabled server definitions retire their affected connections, and helper shutdown closes all transports. URL-mode elicitation remains declined because it is separate from MCP transport OAuth. The native Desktop MCP Manager supports structured configuration changes and raw-config opening; the browser does not gain arbitrary file access. Its **Connect** and **Reconnect** actions recover one configured server with existing credentials, while **Reauthenticate** starts a fresh Desktop OAuth sign-in for an enabled remote server. Existing tokens remain available if the new sign-in is cancelled or fails; successful sign-in replaces them. Manual connection actions are unavailable during an active turn. Non-macOS shared credential adapters remain later parity work. CLI and standalone Desktop use distinct Keychain accounts for MCP OAuth; VS Code uses extension-host credential storage. Existing credentials in the former shared Keychain account are not migrated or deleted, so a new CLI or Desktop login may be needed. Reauthenticating one surface does not change the others.
